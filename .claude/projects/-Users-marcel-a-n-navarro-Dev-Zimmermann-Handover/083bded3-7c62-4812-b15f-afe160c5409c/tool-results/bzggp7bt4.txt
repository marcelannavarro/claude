## Summary

- New workflow `sync-env-vars-to-mrt.yml` — triggered manually from GitHub Actions → Run workflow
- No hardcoded variable names: reads `.env.sample` for the key list, fetches actual values from the selected GitHub Environment via the GitHub API, then intersects the two
- Only keys that are **set and non-empty** in the GitHub Environment are PATCHed to MRT — missing keys are silently skipped so MRT retains existing values
- `scope:personal` and `scope:auto` keys (including `ENVIRONMENT_NAME`) are never synced
- Supports **dry run** mode — shows exactly what would be synced without touching MRT

## How it works

```
.env.sample  →  parse scope:shared + scope:tier keys
                        ↓
GitHub API   →  GET /environments/{target}/variables  (all set vars)
                        ↓
intersection →  keys in both + non-empty value
                        ↓
MRT API      →  PATCH /projects/zimmermann/target/{target}/env-var/
```

## Usage

**GitHub Actions → Workflows → "Sync Env Vars to MRT" → Run workflow**

Select target (`dev` / `test` / `sit` / `uat` / `staging` / `prod`) and optionally enable dry run.

## Review: Requesting Changes

I'm requesting changes on a few items before merge. Two are verified against the live repo and are really yours to call, since you own the CI/CD and env-governance model this touches. (As a Tier 1 workflow it'll also need a second tier-1-approver — GitHub won't let you self-approve.)

### Must Resolve Before Merge

**1. Any write-access contributor can push to `prod` MRT, ungated.**
The job uses `environment: ${{ inputs.target }}`, which *can* enforce approval — but I checked, and `prod`'s `protection_rules` are empty, so a run targeting `prod` won't pause for review. Anyone who can trigger a workflow can PATCH values into the production MRT runtime with no gate. That's a privilege gap versus your own model: `npm run env -- push` is restricted to tier-1-approvers, but this gives write-access devs an ungated path to the same targets. Add required-reviewer protection to the `prod` (and `staging`) environments — the `environment:` wiring already supports it — and document it as a prerequisite. Oversight or intentional? Either way it needs to be in place before this is a prod path.

**2. It syncs CI/tooling secrets into the MRT storefront runtime.**
The workflow selects all `scope:shared` + `scope:tier` keys, but `scope` encodes *sharing* (team-wide vs per-tier), not "belongs on MRT." I pulled the live environments to confirm the consequence: the `shared`/`dev` environments contain `CODERABBIT_API_KEY` (a secret, for the CodeRabbit CLI), `JIRA_URL`, and `CONFLUENCE_URL` — all `scope:shared`, so they're in the syncable set and would be PATCHed into the MRT runtime, which never uses them. Any set `E2E_*` / `PWA_E2E_USER_PASSWORD` / `RETAIL_APP_HOME` (all `scope:tier`) would go too. Fix: sync from an explicit allowlist of real runtime vars, or add an `mrt:` axis to `.env.sample` so tooling/test creds are excluded. It correctly skips `scope:personal`/`auto` already — the gap is that shared/tier still includes non-runtime tooling.

### Should-Fix
- `GH_ENV_READ_TOKEN` is a classic `repo`-scope PAT — full read/write to all repo content, when it only needs to read Environments.
