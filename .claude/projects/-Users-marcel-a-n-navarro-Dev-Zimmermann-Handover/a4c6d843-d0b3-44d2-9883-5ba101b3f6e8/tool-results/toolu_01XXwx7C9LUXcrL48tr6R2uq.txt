Customisation Model\\n----------------------\\n\\nThis project uses the Salesforce PWA Kit's *template extensibility* model. `@salesforce/retail-react-app` is consumed as an unmodified npm dependency, not a forked copy of the repository.\\n\\nAll customisations live in an `overrides/` directory that mirrors the structure of the underlying `@salesforce/retail-react-app` package. This determines how a shopper's session behaves when they cross storefronts (via the country / language selector or the mismatch slide-out):\\n\\n* **Session cookie is shared.** The `httpOnly` SLAS refresh-token cookie set by the SSR layer is first-party to the one domain, so it is presented on requests to any storefront prefix — no cross-domain SSO bridge is needed.\\n* **Tokens are channel-scoped.** A SLAS token carries the site it was issued for, so the SSR layer re-initialises the SLAS context for the destination storefront. Integration Map\\n------------------\\n\\n### 7.1 Classification model\\n\\nEvery integration is placed in one of five **boundary classes** based on where its network call originates. The split is determined by the vendor's documented auth model — a publishable key implies browser-direct is safe; a secret key forces a server-side hop.\\n\\n* **Browser-direct** — call originates from the user's browser. Vendor publishes a publishable/public key designed to ship in the JS bundle (with referrer or origin restrictions where applicable). No secret material is ever exposed.\\n* **MRT-mediated** — call originates from the Node layer that hosts PWA Kit (the SSR pass, a server-only proxy endpoint in the SSR/Node layer, the `/mobify/proxy/` forwarding layer, or a webhook receiver). Used whenever the vendor requires a secret token, whenever an API key must be kept off the browser bundle entirely, or whenever `httpOnly` cookies must be set or read. Credentials are held as MRT environment variables. This includes calls the PWA makes directly to MuleSoft via MRT proxy (rather than routing through SFCC).\\n* **SFCC-cartridge** — call originates from inside Salesforce Commerce Cloud (a Demandware cartridge). The PWA never makes the call; credentials live in SFCC Business Manager.\\n* **via MuleSoft** — SFCC-side, server-to-server through the MuleSoft middleware. The PWA never sees the downstream system.\\n* **Out-of-band** — runs outside the storefront runtime entirely (scheduled feed, build-time pipeline, or system-to-system integration that bypasses the PWA and often SFCC too).\\n\\nA single integration can span multiple classes — e.g. Adyen is `SFCC-cartridge` for `/payments` calls and `Browser-direct` for the Drop-In SDK; Global-e is `Browser-direct` (checkout handoff — iframe embed) and `SFCC-cartridge` (pricing feed); GiveX is `via MuleSoft` / server-side NewStore-adapter for issue/validate/redeem/refund and `MRT-mediated` for balance checks. SSR, SEO, and GEO Foundation\\n-------------------------------\\n\\n### 8.1 SSR (DMU-030)\\n\\nAll product, category, and content pages will use SSR for full crawlability by search engines and AI bots without dependence on client-side JS. The PWA Kit SSR pipeline is preserved end-to-end. Componentry that cannot SSR is rendered through a hydration-safe boundary that still emits SEO-relevant markup on the server. Global state stores are initialised per request to prevent state leaking across SSR responses.\\n\\n#### 8.1.1 SSR vs CSR by page type\\n\\nPWA Kit always runs the SSR pipeline — every page is server-rendered to some degree. The practical distinction is what content is rendered on the server vs fetched after hydration on the client.\\n\\n| Page type | Pattern | Rationale |\\n| --- | --- | --- |\\n| PDP, PLP, content pages, homepages, boutique pages | **Full SSR** — markup and data rendered on the server | Indexable, SEO- and LCP-critical |\\n| Cart, checkout, My Account, order history, wishlist, address book | **SSR shell + CSR data** — server renders the layout, header, footer, and skeleton; `@salesforce/commerce-sdk-react` hydrates personalised data (basket lines, customer profile, orders) client-side after hydration | Personalised, per-session, behind authentication. No SEO value (blocked in `robots.txt` — §8.3). Server-rendering personalised data would defeat edge caching and risk state leaking across requests |\\n| Search results, filtered PLP states | **SSR shell + CSR data** | Blocked in `robots.txt`; filter / sort state is client-driven |\\n\\nThe \\\"SSR shell + CSR data\\\" pattern still gives the user instant first paint of the page chrome — only the personalised payload waits on hydration. No page is purely client-rendered.\\n\\n### 8.2 Canonicals & hreflang\\n\\nCanonical tags on every indexable page; filtered PLPs canonicalise to the unfiltered base PLP. hreflang on canonical PDPs only, delivered via XML sitemap, consolidated to ~12 regional/language-level tags. Detailed canonical/hreflang rules are specified in the functional requirements.\\n\\n### 8.3 Sitemaps & robots\\n\\nPer-storefront / per-locale XML sitemaps refreshed daily, excluding disabled and deleted pages (DMU-026). `robots.txt` permits indexable pages (including the bag page) and blocks checkout, account, search results, and filtered URL parameters. URLs blocked in `robots.txt` never appear in a sitemap.\\n\\n### 8.4 Structured data\\n\\nCustom JSON-LD per the Sparro templates, rendered server-side so crawlers see it on the first response:\\n\\n* **PDP:** Product + Merchant Listing Schema (`ProductGroup` + variant `Product`s), with real-time inventory driving availability.\\n* **PLP:** CollectionPage + BreadcrumbList + ItemList Schema (ItemList reflects the initial SSR'd product batch).\\n* **Boutique pages:** LocalBusiness / ClothingStore Schema per location.\\n* **Homepages:** Organisation + WebSite Schema per regional storefront, with per-prefix `WebSite` nodes (including the Global-e international paths `/en-ca/` and `/en-ch/`).\\n\\n### 8.5 URL strategy\\n\\n* Product URL: `/[prefix]/[name]-[colour].html` — the `.html` suffix is preserved to maintain existing indexed URLs.\\n* Category URL: `/[prefix]/[slug]` (no suffix), with 301 redirects from legacy paths.\\n* 301 redirects for every URL that changes as a result of migration (products, categories, content). Implemented at the CDN/edge layer to keep application-layer impact minimal.\\n\\n### 8.6 GEO (DMU-042)\\n\\nNo GEO-specific features in launch scope. The technical foundations enabling post-launch GEO — SSR, structured data, canonicals, XML sitemaps — are in place at go-live so no architecture decision blocks future activation.\\n\\n---\\n\\n9. Performance Strategy\\n-----------------------\\n\\nLCP at p75 mobile is the binding constraint and the de-facto cap on third-party script weight.\\n\\n| Metric | Target |\\n| --- | --- |\\n| LCP (mobile p75) | ≤ 2 s |\\n| Lighthouse Performance | ≥ 0.80 |\\n| Lighthouse Accessibility | ≥ 0.90 |\\n| Lighthouse Best Practices | ≥ 0.90 |\\n\\n### 9.1 Third-party defer rule\\n\\nAnything loaded via Didomi callback (GTM — which loads Meta, GA4, and other GTM-housed tags via Tell No Lies; Narvar EDD widget; Inside Chat) is deferred, async-loaded, or injected post-hydration so it does not block LCP. **Measmerize** (Find My Size / size guide — PDP only) likewise defers behind LCP — the script injects after the product hero image has loaded. **reCAPTCHA** likewise loads only on register/login form interaction, so it never sits on the critical path of any other page (consent treatment per §11.1). **Exception (AAB-004):** Optimizely Web is a PWA-direct head tag (not a GTM tag) and deliberately loads in the page head **before render** to prevent A/B flicker, scoped to the US storefront where Optimizely runs. **Crazy Egg (AAB-005)** loads async and post-Didomi-consent. Editorial pages may also embed a Vimeo video by URL where preferred (HPC-004) — the product/editorial split above is the expected pattern, not a hard restriction.\\n  + Across both: `preload=\\\"metadata\\\"` by default; autoplay reserved for muted, short-loop hero clips only.\\n* Dynamic imports for heavy non-initial components.\\n* Parallel data fetches; no client-side waterfalls. Treat CI numbers as regression indicators; treat Stage numbers as the contractual ones.\\n\\n> **SSR connection pool tuning:** the initial per-pool connection caps defined in §12.1 are derived from expected concurrency, not observed traffic. This section covers how to limit the *spread* of an attack or outage — ensuring a degraded integration cannot consume shared resources and take down unrelated features.\\n\\n#### Edge (outside the PWA — Infrastructure / SI Partner)\\n\\n* **Web Application Firewalls + rate limiting** is the primary lever for volumetric attacks and credential-stuffing.\\n* **SFCC Business Manager** provides API-level rate limiting for SFCC endpoints, independent of the storefront edge.\\n\\n#### SSR layer (inside the PWA)\\n\\n`overrides/app/ssr.js` makes server-side `fetch` calls directly (token exchange, JWKS, SF Payments metadata). Undici's `dispatcher` option (the per-call `dispatcher` option on individual `fetch()` invocations) allows each upstream origin to be given its own connection pool with an independent cap. This prevents a slow or flooded integration (e.g. checkout APIs) from exhausting connections for unrelated origins (e.g. Contentful, JWKS).\\n\\n> **Implementation note:** the per-call `dispatcher` option is safer than the `setGlobalDispatcher` in a managed environment (MRT) since it does not touch the global dispatcher that Salesforce internal libraries may rely on. The `commerce-sdk-react` hooks manage their own HTTP client server-side (Commerce SDK) and are not affected in either approach.\\n\\nThe connection pool split is an engineering decision — the right pool boundaries and sizes depend on observed traffic patterns and the integration map in §7. Tag/class/DOM-position selectors are not used. This doubles as a continuous accessibility check.\\n\\n---\\n\\n14.
