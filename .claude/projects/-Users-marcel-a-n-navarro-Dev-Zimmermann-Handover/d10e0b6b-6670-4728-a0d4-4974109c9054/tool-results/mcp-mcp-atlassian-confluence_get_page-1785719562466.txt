Problem Statement</h2><h3 local-id=\\\"305295f35a2d\\\">1.1 Context</h3><p local-id=\\\"763206280d56\\\">Zimmermann's storefront runs on SFCC B2C Commerce with a PWA Kit front end hosted on Managed Runtime (MRT). Editorial and CMS content (banners, homepage modules, navigation, footer, size guides, editorial blocks) is owned by Contentful and managed by the Zimmermann content team; commerce data (products, pricing, inventory, orders) is owned by SFCC. A dedicated Contentful squad will own the full Contentful setup under a separate statement of work; the Accenture squad must build and document the SFCC-side integration before that squad onboards.</p><h3 local-id=\\\"e4355ee31376\\\">1.2 Problem</h3><p local-id=\\\"8374ad8d55ad\\\">Editorial content authored in Contentful must render on the correct SFCC storefront pages. Some content is global; some must appear only on a specific category or product page. Contentful holds no knowledge of the SFCC catalogue, and the two systems must remain decoupled. The team needs one defined, correct mechanism for the PWA/MRT layer to decide which Contentful entries render on which SFCC page, cache-safely and consistently across the storefronts, together with a clear account of what the Accenture squad must build on the SFCC side (content types, consuming components, rendering logic, locale configuration, integration wiring) before the Contentful squad onboards.</p><h3 local-id=\\\"77c3909041cf\\\">1.3 Impact if Not Solved</h3><p local-id=\\\"3de45c46a30b\\\">Without a defined pattern the squad risks building inconsistent per-component ID-matching logic, coupling Contentful to the SFCC catalogue, or serving cached editorial content on the wrong category or product pages. The incoming Contentful squad would lack a briefing artefact, and integration blockers (credentials, per-environment configuration, unresolved content ownership) would surface late in the build.</p><h3 local-id=\\\"8cd6cedbd128\\\">1.4 Success Criteria</h3><ol local-id=\\\"95f30849ddf2\\\" start=\\\"1\\\"><li local-id=\\\"7bf8de86aab5\\\"><p local-id=\\\"5b64b44c797c\\\">One documented mechanism exists for scoping and rendering Contentful editorial content on the correct SFCC pages, decoupled from the SFCC catalogue.</p></li><li local-id=\\\"1c8ca9e30030\\\"><p local-id=\\\"239326485bf6\\\">The SFCC-side build scope (content types, consuming components, rendering logic, locale configuration) is enumerated and traceable to Jira stories.</p></li><li local-id=\\\"9dbaf4d87a13\\\"><p local-id=\\\"c584f32d9f35\\\">The Accenture versus incoming-Contentful-squad handoff boundary is defined.</p></li><li local-id=\\\"e8804c54fbbf\\\"><p local-id=\\\"49bd0457f245\\\">Blockers and dependencies for the Contentful squad's onboarding are identified with owners.</p></li><li local-id=\\\"5f9eba23ed7c\\\"><p local-id=\\\"89eede0dab7c\\\">The design is cross-checked against the codebase, Jira, and Confluence for accuracy.</p></li></ol><p local-id=\\\"722ad4d78dad\\\"><em>These criteria map to the validation in Section 6.</em></p><hr data-layout=\\\"wide\\\" data-width=\\\"760\\\" local-id=\\\"70d7e136afea\\\"/><h2 local-id=\\\"73099763b0aa\\\">2. SFCC ID + MRT SSR-side filtering</h4><p local-id=\\\"6aa44ca94122\\\">SFCC product and category IDs are stored as plain, non-localized ShortText fields (<code>sfccProductId</code>, <code>sfccCategoryId</code>) on the Contentful content type. At render time the MRT SSR layer fetches all published entries of a content type for the current locale, filters them by matching the ID field against the current page context, and passes only the matched entries to a presentation-only React component. A null ID means \\\"show on all pages of this type\\\". This fits the decoupling and SSR/SEO constraints in Section 2 and is detailed in Section 5.</p><h4 local-id=\\\"08f6482e220b\\\">Option B - Mirror the catalogue into Contentful (not selected)</h4><p local-id=\\\"60b15113e611\\\">Editors would pick real SFCC products/categories via Contentful reference fields backed by a synchronised copy of the catalogue. This removes the typo risk but requires a sync pipeline and couples the two systems; it is disproportionate to the current editorial volume.</p><h4 local-id=\\\"c1e5b714beef\\\">Option C - Client-side filtering <em>(Discarded)</em></h4><p local-id=\\\"39804cbed2bc\\\">Discarded: fetching all entries and filtering in the browser keeps editorial content out of the SSR HTML, which violates the SSR-first / SEO constraint and pushes ID-matching logic into components.</p><hr data-layout=\\\"wide\\\" data-width=\\\"760\\\" local-id=\\\"097d199f24cc\\\"/><h2 local-id=\\\"a0c1911190ba\\\">4. Recommended Option &amp; Rationale</h2><h3 local-id=\\\"42106bfeb60a\\\">4.1 Recommended Option</h3><p local-id=\\\"b157d8979ba5\\\"><strong>Option A - SFCC ID as a non-localized ShortText field, resolved by MRT SSR-side filtering.</strong></p><h3 local-id=\\\"9cd9f0e00765\\\">4.2 Rationale</h3><p local-id=\\\"f31a7d46f8be\\\">Option A is the only approach that keeps Contentful decoupled from the SFCC catalogue while placing editorial content in the server-rendered HTML (satisfying the SSR/SEO constraint) and keeping components presentation-only. Option B solves the authoring typo risk but pays for it with a sync pipeline and coupling not justified by the current editorial volume; Option C is disqualified by the SSR/SEO constraint. Reference-resolution (turning an ID into rendered commerce data) is out of scope for this document and is owned by SFCC-238.</p><h3 local-id=\\\"3e0c5c5dd46d\\\">4.3 Trade-offs Accepted</h3><ul local-id=\\\"1c3389c6777e\\\"><li local-id=\\\"9b0737edaa7f\\\"><p local-id=\\\"3cac43683ec1\\\"><ac:inline-comment-marker ac:ref=\\\"4b418c45-0b57-4570-98d4-0ee087453bc3\\\">Authors enter SFCC IDs by hand with no referential-integrity guardrail (typo risk).
