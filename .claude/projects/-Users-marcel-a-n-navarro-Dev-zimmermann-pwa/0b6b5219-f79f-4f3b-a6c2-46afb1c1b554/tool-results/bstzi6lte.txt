## Sweep — internal consistency

- **🔴 UNIFORM, confirmed by direct file absence + exhaustive grep — the promised single source of truth doesn't exist.** `zimmProductCardShared.ts` was never created. Consequence, verified directly: 10 distinct `data-card-slot` string literals are typed once in each producing molecule (`zimmProductCardMedia/index.tsx`, `zimmProductCardContent/index.tsx`) and re-typed again as raw strings inside CSS selectors in `zimmProductCard.css.ts` (17+ occurrences) and again inside `querySelector(...)` calls across three test files. `HOVER_CAPABLE_QUERY` (`'@media (hover: hover) and (pointer: fine)'`) is independently defined in both `zimmProductCardMedia.css.ts` and `zimmProductCard.css.ts` — the latter's own docblock admits this is deliberate non-sharing. The only synchronisation mechanism anywhere is a comment reading *"Do not rename these values without updating that recipe too."* Both values currently agree, but nothing — no compiler, no lint rule, no test — would catch it if they stopped agreeing. This is precisely the drift risk `overrideStyling.md`'s "Cross-file shared values" section exists to prevent, and the plan cited the exact right precedent (`zimmColourSwatchGroupShared.ts`) for avoiding it. `CARD_BP` fares better — both consuming files import `breakpoints` directly from `theme/foundation`, a genuine single source, just not the named alias plan.md specified.
- **🟡 UNIFORM, correctly-propagated pre-existing gap — no semantic "selected" border token exists.** `zimmSizeChip.css.ts` reaches for `var(--zimm-color-border-focus)` to mean "selected" (self-flagged in its own comment). Verified: `theme/foundation/colour.ts`'s border alias tier has no `selected`/`active` token at all, and the direct exemplar (`zimmColourSwatch.css.ts`) already does the identical thing with no caveat. This build correctly matched precedent rather than inventing a new pattern — the gap is a foundation-level should-fix (a `--zimm-color-border-selected` token), not a defect introduced here.
- Every recipe otherwise matches shape (`parts` convention, registration pattern, `Zimm*` naming); every component matches the four/five-file structure; no value found typed three times in disagreement.

## Sweep — external conformance

- **Against the exemplar** (`ZimmColourSwatch`/`ZimmColourSwatchGroup`, PR #64/#70) — matches on export/props naming, recipe-key pattern, file-set shape, and registration style. Roving-tabindex keyboard nav is independently re-implemented rather than shared (`handleChipsKeyDown` vs. `handleSwatchesKeyDown`) — a DRY tension, but consistent with this repo's own Hard Rule #5/#6 stance against refactoring upward into an already-shipped component. Not flagged as a defect.
- **Against `.claude/rules/*`** — holds across the whole feature: token usage is `var(--zimm-*)` throughout with zero bare Chakra keys, imports are clean (no `../../../../` chains, no base-path shadowing, no later-sprint references), accessibility spot-checks (badge is genuinely non-interactive per §4c/§4f, close/arrows are real `<button>`s with `aria-label`s, every `<img>` has `alt`) all confirmed by reading the actual JSX, not the docblocks describing it.
- **🟡 ONE-OFF — Storybook categorisation.** `ZimmSlideIndicator` shipped under `Commerce/`; plan.md's own Step 1 explicitly said `Elements/`. Per `components.md`'s own tiebreaker ("what does this component know about?"), it's a generic count/index dot-indicator with zero product knowledge — `Elements/` is the correct call, and it looks like it was pulled into `Commerce/` by proximity to its five product-aware siblings rather than evaluated on its own.
- **🔴 CONFIRMED, ONE-OFF but high blast radius — Dani Rivett's carousel-suppression instruction has no code path.** Gate finding #17 quotes Dani (Jira comment 13880): *"we do not want the badge displayed on the Homepage **or** on the Recently Viewed product carousel"* and *"we don't want the hover action (model photo) on the homepage **or** the recently viewed carousel."* The shipped `VARIATION_CONFIG` implements the Homepage half only — `home.showBadge = false`, `home.showHoverImageSwap = false` — and the organism's own docblock quotes Dani twice, both times truncating exactly at "the homepage," never reaching the carousel clause of the same sentence (verified directly, lines 92-93 and 111-112 of `zimmProductCard/index.tsx`). Plan.md separately states `'recently-viewed'` is not a real union member — a rail consumer would reach for `variation: 'plp'`, which ships `showBadge: true` / `showHoverImageSwap: true` — the opposite of what Dani asked. Because plan.md and findings.md live outside this repository, gate finding #17 itself is invisible to anyone reading the shipped code or a future PR — nothing in any docblock, OQ entry, or "Known gaps" note carries this forward. **This isn't a wrong call for SFCC-236 itself** (SFCC-83's rail is out of scope for this ticket) **— it's a traceability gap**: the one place this instruction could still reach SFCC-83's future builder (an in-code note) doesn't have it.

## UNIFORM findings (the point of this phase)

1. **No shared constants module — `zimmProductCardShared.ts` was planned, cited by precedent, and never built.** Confirmed independently by both audits. Cheapest real fix: extract the existing (currently-agreeing) literals into the file the plan already named, matching `zimmColourSwatchGroupShared.ts`'s pattern exactly.
2. **A written product instruction (Dani's carousel clause) has no surviving trace in the shipped code**, despite the same instruction's other half being carefully implemented and cited twice. Worth a one-line docblock addition stating the carousel half is deliberately left to SFCC-83, so it isn't lost a second time.
3. **A pre-existing foundation gap (no semantic "selected" border token) has now been propagated into a second component.** Not this build's fault, but it will recur again in the next selectable-control component built against the same gap unless the foundation adds the token.
