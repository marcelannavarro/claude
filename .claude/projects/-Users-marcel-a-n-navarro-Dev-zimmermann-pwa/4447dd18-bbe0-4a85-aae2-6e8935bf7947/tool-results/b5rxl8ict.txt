### 4.4 🟠 The `Breadcrumb` override breaks the SFCC bridge contract

`.claude/rules/overrideStyling.md` > *The SFCC bridge pattern (shared components only)*: if a component is used internally by SFCC's own base components, its **default export must stay a faithful, undecorated port** — full original prop surface, brand styling behind a named export.

- `node_modules/@salesforce/retail-react-app/app/components/product-view/index.jsx:75` → `<Breadcrumb categories={category} />`
- `node_modules/@salesforce/retail-react-app/app/pages/product-list/partials/page-header.jsx:20` → `<Breadcrumb categories={category.parentCategoryTree} />` (**the PLP breadcrumb**)

The override is not a faithful port. Divergences that now apply to the PLP:

| Base | Override | Impact |
|---|---|---|
| `({categories, ...rest})`, `...rest` spread onto the root | `{categories, currentPage}`, no rest spread (`index.tsx:47`) | pass-through props silently dropped |

| `className="sf-breadcrumb"`, `data-testid="sf-crumb-item"` | neither | any selector keyed on these breaks (none in-repo today) |
| `useStyleConfig('Breadcrumb')` — theme-driven | styles hardcoded in the component (`index.tsx:22-35`) | breaks the branch's own theme-recipe pattern |
| `<ChevronRightIcon>` separator | literal `/` text (`index.tsx:39`) | **PLP breadcrumb visual changes**, unreviewed by design |
| Chakra `Breadcrumb`/`BreadcrumbItem`/`BreadcrumbLink` | raw `Box`/`Text` | loses Chakra's breadcrumb a11y primitives |
| imports `categoryUrlBuilder` from `app/utils/url` | reimplements it inline (`index.tsx:10-11`) | DRY (`conventions.md`); silently diverges if base changes |

*Checked and NOT a finding:* base `categoryUrlBuilder` ignores its locale argument (`node_modules/.../app/utils/url.js:90`), so the inline copy is behaviourally identical — **no locale-prefix regression**. Base also uses raw `RouteLink`, so no `Link`-component regression either.

## 7. Honest overall assessment

**Verdict: a solid *component* base sitting on an unsafe *integration*. Keep the components, rework the page and the two override-shadow decisions.**

### What is genuinely good — keep it
- **`PdpProductInfo` + its theme recipe is exemplary.** Correct `useMultiStyleConfig` pattern, `Zimm`-prefixed and registered, every escape hatch documented with a written exit path. This is the pattern the rest of the branch should be migrated to.
- **Accessibility was taken seriously and is real, not claimed.** `h1` for the product name, `nav`/`ol`/`li` breadcrumb semantics, `aria-current="page"`, `aria-hidden` separators, and a Storybook `play` that actually asserts tab order (`breadcrumb/index.stories.tsx:46-52`).
- **Storybook coverage is complete and correctly categorised** — all four surfaces, `play` functions only where there's interaction.
- **Gherkin-first E2E workflow followed** — `.feature` before spec, correct `@pdp`/`@SFCC-89` tags on all 10 tests, sensible page-object locators using accessible selectors first.
- **The `generateRegistry.mjs` consumer-count fix is a real, well-reasoned improvement** (specifier anchoring instead of substring grep, plus a single file-walk instead of N subprocesses). It happens to be unrelated to SFCC-89.
- **`tsc` and Vitest are green.**

### What makes it not mergeable as-is
1. **A Tier 1 file was changed after the PR body itself said it was blocked pending approval.** That is the single most serious thing here — not because dompurify is wrong (it's the right call for `dangerouslySetInnerHTML`), but because the process gate was identified and then walked through. It also drags in 16 MB / jsdom on the SSR path with no bundle-budget verification.
2. **Merging this removes add-to-bag and all SEO metadata from the PDP.** Whether that's in scope for "static product information" is a product question no one has answered in the PR. It cannot merge to `develop` without an explicit answer.
3. **The `Breadcrumb` override silently restyles the PLP.** It shadows a shared SFCC component and is not a faithful port — the PLP breadcrumb loses its chevron separators and its theme config. Nobody asked for that and the PR body doesn't mention the PLP at all.
4. **The `Pages/PDP` story is a copy-paste of the page**, so the one artefact reviewers will actually look at is not the thing being reviewed.

### Effort to make it good
Roughly a day of focused work, and it is mostly *decisions*, not code:

- **10 minutes:** `npm run lint:fix` (all 5 errors auto-fixable); delete the redundant `.gitkeep` and the dead `: null`.
- **Half a day:** move `Breadcrumb` and `ZimmPageToolbar` styling into `theme/components/*.ts` recipes (the author already knows how — `3e1686b` is the template); `react-intl` the four hardcoded strings; make `ZimmPageToolbar`'s padding responsive; add the missing per-site SKUs or a hard configuration error.
- **Half a day:** extract a presentational `PdpLayout` so the page and the story stop duplicating; add a Vitest for the breadcrumb-assembly/degradation logic; move `index.test.ts` → `utils/productData.test.ts`.
- **Blocking, needs humans not code:** Integration sign-off on `isomorphic-dompurify` (or swap for a lighter sanitizer); a product/Squad-A decision on the base-PDP replacement scope; UI Designer notification for the two Tier 2 theme files; a squad-lead call on the PDP ownership move.

### Takeover recommendation
Do **not** rebase-and-continue on top of this. Land the four blocking decisions first — dependency approval, PDP replacement scope, breadcrumb-shadow strategy, theme-file owner sign-off — because two of them (scope, breadcrumb) may delete or restructure a meaningful slice of the code. The component layer (`PdpProductInfo`, `ZimmPageToolbar`, the stories, the `.feature`) is worth carrying forward almost verbatim.
