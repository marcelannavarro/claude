## 2. What a new PDP component must look like structurally

### 2a. The naming families — keep them straight

| Family | Case | Where | Live examples on this branch |
|---|---|---|---|
| SFCC override dirs (shadow a base module) | **kebab-case**, matching the base filename exactly | `overrides/app/components/<kebab>/` | `breadcrumb/`, `header/`, `icons/`, `_app-config/` |
| Zimmermann-authored components | **camelCase** | `overrides/app/components/<camel>/` or `ui-kits/<tier>/<camel>/` | `pdpProductInfo/`, `pageContainer/`, `button/`, `ui-kits/atoms/zimmPageToolbar/` |

### 2e. Concrete path example — a new PDP component per the rules as written

For a hypothetical `PdpSizeSelector`:

```
overrides/app/components/ui-kits/molecules/pdpSizeSelector/
  index.tsx            ← named export PdpSizeSelector + default; props type at top of file
  index.stories.tsx    ← title: 'Commerce/PdpSizeSelector'  (commerce-aware → Commerce/, per components.md)
  index.test.ts        ← only if logic-heavy
overrides/app/theme/components/pdpSizeSelector.ts   ← exports `ZimmPdpSizeSelector` (parts + baseStyle)
overrides/app/theme/components/index.ts             ← add import + key to the `components` object
```

Existing precedent to copy verbatim — `pdpProductInfo` **[V]**:
- Component consumes the recipe via `useMultiStyleConfig('ZimmPdpProductInfo', {})` and applies parts
  as `__css={styles.<part>}` (`pdpProductInfo/index.tsx:27, 32`).
- Recipe declares `parts: ['name','price','description','modelInfo','styleCode']` and a `baseStyle`
  per part (`theme/components/pdpProductInfo.ts:56-90`).
- Values that genuinely can't live in `baseStyle` (conditional margins) are exported as named consts
  from the theme file and imported by the component — `SPACE_DESCRIPTION_TO_META`,
  `SPACE_MODEL_INFO_TO_STYLE_CODE` (`pdpProductInfo.ts:47,50` → `index.tsx:4,42,53`). That is the
  house pattern for "styling that must be at the call site": **name it in the theme file anyway.**
- The theme file carries a header comment explaining each level-4 (`var(--zimm-*)`) escape and why
  no `textStyle` exists for it yet (`pdpProductInfo.ts:1-33`).

**Chakra scale caveat (matters for any new recipe):** `theme/index.ts:51-58` registers only
`borderWidths, breakpoints, colors, fonts, space, textStyles, components`. `fontSizes`, `sizes`, and
`transition` are **deliberately not registered** because Zimmermann and Chakra use the same key names
for different values (`theme/index.ts:26-49`). So `fontSize="2xs"` in a recipe silently resolves to
Chakra's 10px, not Zimmermann's 14px — which is exactly why `pdpProductInfo.ts` uses
`fontSize: 'var(--zimm-font-size-2xs)'`. `spacing` **is** registered as `space`, so `marginBottom: 'l'`
is safe. **[V]**

## 3. The component registry

**What it is:** `scripts/generateRegistry.mjs` (37 kB) scans `overrides/app/{components,hooks,utils,pages}`
**plus** `node_modules/@salesforce/retail-react-app/app/`, and writes markdown tables to
`.claude/registry/{components,hooks,pages,routes,utils}.md` so Claude reads a table instead of grepping.
Columns: Component · Origin · Path · Props · Tier · Squad · Consumers · Last touched · Description. **[V]**

**Does a new PDP component register itself? No — it is fully automatic.** Nothing is hand-maintained
**[V]**:
- `generateRegistry.mjs:670` — `origin: baseMatch ? 'Override' : 'Custom'`, matched by folder-name
  variants (`folderVariants()` at `:105-109` tries kebab↔camel), so a camelCase Zimmermann folder with
  no base twin is auto-classified `Custom`.
- Tier and squad are derived from `.claude/rules/` path lists (`generateRegistry.mjs:~112` onward).
- `scripts/hooks/pre-commit:49-62` regenerates and `git add`s `.claude/registry/` whenever a staged path
  matches `overrides/app/{components,hooks,utils,pages}/` or `routes.tsx`.
- `.claude/settings.json` PostToolUse `Edit|Write` → `.claude/hooks/registryUpdate.sh` → incremental
  `--file=` regen (skips `*.test.*`, `*.stories.*`, `ContentfulDefinition`).
- `package.json` `postinstall` runs `npm run generate:registry`.

**Is it a blocker? No.** The registry is **already on `develop`** (`git ls-tree develop` lists all five
`.claude/registry/*.md`, `scripts/generateRegistry.mjs`, and `.claude/hooks/registryUpdate.sh`) and
therefore on this branch. **[V]** `feature/f2r-component-registry` adds one extra output
(`.claude/registry/mocks.md`) and generator refinements, but nothing the PDP work depends on.

The premise in the task brief that the registry might be "not yet merged to develop" is **false** — it
is merged. **[V]**

Minor: `.claude/registry/components.md:84` shows `ZimmPageToolbar`'s props flattened across its
discriminated union (`variant: 'breadcrumbs', heading: string, …`). Commit `cf17c3d` on this branch
("teach extractTsProps to parse discriminated union Props types") fixes the generator; the checked-in
`.md` is stamped `2026-08-20` and predates it. Cosmetic — a regen will correct it. **[V]**

## 4. Intercept traps — which apply

### (a) base-path import → unstyled base component in Storybook & Vitest

**Mechanism confirmed [V]:**
- `package.json` `ccExtensibility: {extends: '@salesforce/retail-react-app', overridesDir: 'overrides'}`
  — read by the pwa-kit webpack plugin, i.e. **real builds only**.
- `.storybook/main.js:25` aliases `'@salesforce/retail-react-app'` → `node_modules/@salesforce/retail-react-app`,
  bypassing the resolver entirely.
- `vitest.config.ts:17-20` aliases only `~` and `app` — it never mentions
  `@salesforce/retail-react-app`, so those imports go straight to `node_modules` by normal resolution.

**Does it apply to the PDP work today? Not yet.** I cross-referenced every base-path import in
`overrides/` against every existing override directory. The **only** collision in the entire repo is
`icons`, and it is deliberate (`overrides/app/components/icons/index.tsx:73` re-exports from the base
icon set — that's the documented single-source-of-truth pattern; `header/index.tsx:44` imports the
same base path). **[V]**

Every other base-path import in `overrides/` resolves to a module we do **not** override
(`shared/ui`, `constants`, `contexts`, `utils/*`, `seo`, `link`, `loading-spinner`, `search`,
`with-registration`, `product-scroller`, `section`, `hooks/use-multi-site`, `hooks/use-current-basket`,
`hooks/use-navigation`, `hooks/use-einstein`, `app/theme`, `app/routes`, `app/mocks/standard-product`).
Per `overrideStyling.md` that is simply correct. **[V]**

**It becomes live the moment PDP work adds an override.** Concretely: if you create
`overrides/app/components/swatch-group/`, then `product-view/index.jsx:55` imports it by base path —
correct in the app, base-unstyled in Storybook/Vitest. Same for `image-gallery` (`product-view:44,48`),
`display-price` (`product-view:53` + 5 others), `quantity-picker` (`product-view:50`),
`breadcrumb` (**already overridden**, and `product-view/index.jsx:45` imports it by base path — so the
moment anything writes a story or test that renders base `ProductView`, it will render the *base*
breadcrumb, not ours). **[V]**

Rule for new PDP code, per `overrideStyling.md` > "Importing an already-overridden component":
import an already-overridden sibling by **relative path** (`'../breadcrumb'`), never by base path. The
PDP page already does this correctly at `index.tsx:6,8,9` (all relative `../../components/…`). **[V]**

### (b) `shared/ui` barrel — a relative re-export the resolver never rewrites

**Confirmed with hard numbers [V]:**
- `node_modules/…/app/components/shared/ui/index.jsx` is a pure barrel of **103** relative re-exports
  (`export {Box} from './Box'`, `export {Button} from './Button'`, …).
- Base files importing the barrel path `…/components/shared/ui'`: **212**.
- Base files importing a deep `…/components/shared/ui/<Name>` path: **0**.

Because the re-export is relative (`'./Button'`), the `ccExtensibility` resolver — which only rewrites
`@salesforce/retail-react-app/...` specifiers — never sees it. Creating
`overrides/app/components/shared/ui/Button/index.tsx` would intercept **zero** of those 212 consumers.
You would additionally have to override the barrel itself.

**Does the PDP work depend on this? No, and it should not start.** The sub-modules are one-line Chakra
re-exports (`shared/ui/Skeleton/index.jsx` is literally `export {Skeleton} from '@chakra-ui/react'`) —
there is nothing to override there. No `overrides/app/components/shared/` exists on HEAD or `develop`
(`git ls-tree` = 0 on both). The correct lever for `Box`/`Text`/`Skeleton` styling is the Chakra theme,
which is already how the repo does it. **[V]**

Style consistency note: `breadcrumb/index.tsx:3` imports `Box, Text` from `@chakra-ui/react` directly
while `product-detail/index.tsx:5` and `zimmPageToolbar/index.tsx:3` import them from the SFCC
`shared/ui` barrel. Functionally identical (the barrel is a Chakra re-export), but pick one for new
files. **[V]**

### (c) conditional render of an alternate module

**The `_app` checkout swap is real but does not touch PDP [V]:**
`node_modules/…/app/components/_app/index.jsx:216` computes `const isCheckout = /\/checkout$/.test(location?.pathname)`,
then `:403` swaps `Header` → `CheckoutHeader` and `:484` `{!isCheckout ? <Footer /> : <CheckoutFooter />}`.
`/product/:productId` never matches that regex, so PDP always gets the normal Header/Footer.
**No PDP equivalent of this trap exists.** **[V]**

**Two adjacent things worth knowing anyway [V]:**
1. **`<Island hydrateOn='visible'>`.** Base wraps `ProductView`, `InformationAccordion`, and all three
   `RecommendedProducts` in `<Island>` (`product-detail/index.jsx:674, 788, 816, 831, 846`) — deferred
   hydration. Our override uses no Island. If PDP work reintroduces base components, they will hydrate
   eagerly unless Island is reintroduced too. Relevant to the ≤2s p75 mobile LCP budget in AGENTS.md.
2. **Set/bundle branch.** `product-detail/index.jsx:672` renders a structurally different tree for
   `isProductASet || isProductABundle` (per-child `ProductView` + `InformationAccordion`). Our override
   renders one shape for every product type, so a set or bundle SKU will render as a plain product. Not
   an override-bypass — a functional gap. **[V]**
3. `ProductView` is rendered from 6 places, not just PDP (`product-view-modal/index.jsx`,
   `product-view-modal/bundle.jsx`, `bonus-product-view-modal/index.jsx`, + tests). An override of it
   is a Tier-2-scale blast radius, not a PDP-local change. **[V]**

## 5. Data layer

**Rule** (`.claude/rules/components.md` > Composition): anything under `overrides/app/components/`
receives data as props and calls **no** data-fetching hook — not `useProduct`, not any
`@salesforce/commerce-sdk-react` / React Query hook. Fetching lives in `overrides/app/pages/`. **[V]**

**The PDP obeys this today** — `useProduct`/`useCategory` are called only in
`overrides/app/pages/product-detail/index.tsx:21-31`; `PdpProductInfo`, `Breadcrumb` and
`ZimmPageToolbar` are all pure prop-driven. **[V]**

**Type chain [V]:**

```
useProduct  →  node_modules/@salesforce/commerce-sdk-react/hooks/ShopperProducts/query.d.ts:28
               UseQueryResult<DataType<Client['getProduct']>>
            →  commerce-sdk-isomorphic ShopperProductsModelTypes.Product
               (node_modules/commerce-sdk-isomorphic/lib/index.esm.d.ts:59783-59835)
```

Fields the PDP already reads, all optional on the type: `id: string` (the only required one), `name?`,
`price?`, `currency?`, `shortDescription?`, `longDescription?`, `primaryCategoryId?`. Also available and
unused: `imageGroups?: Array<ImageGroup>`, `variants?`, `variationAttributes?`, `variationValues?`,
`master?`, `inventory?`/`inventories?`, `type?: ProductType`, `setProducts?`, `bundledProducts?`,
`productPromotions?`, `priceRanges?`, `prices?`, `pageMetaTags?`, `slugUrl?`. **[V]**

**Custom SFCC attributes.** The type ends in `& { [key: string]: any }` (`index.esm.d.ts:59834`), so any
`c_*` attribute typechecks as `any` for free. The repo deliberately does **not** rely on that — it
declares a narrowed intersection type instead:

```ts
// overrides/app/types/commerce.ts:7-10
export type ProductWithSizeFit = NonNullable<ReturnType<typeof useProduct>['data']> & {
  c_sizeFit?: string;
};
```

Used at `product-detail/index.tsx:78` as `(product as ProductWithSizeFit | undefined)?.c_sizeFit`.
**Copy this pattern for every new `c_*` attribute** — add the field to `commerce.ts`, re-export from
`types/index.ts`. It satisfies AGENTS.md > Type Definitions ("don't re-declare types already exported by
`commerce-sdk-isomorphic`") by deriving from `ReturnType<typeof useProduct>` rather than restating it. **[V]**

**Category shape:** `useCategory(...).data.parentCategoryTree` → `Array<PathRecord>` where

**Mocking policy.** AGENTS.md > Rules: no MSW / hardcoded fixtures in **production paths**. Stories and

### 6c. E2E scoping — a PDP change runs the FULL suite

`qa.yml:97-102` defines exactly one area allow-list, `e2e_homepage`. There is **no `e2e_pdp` group**,
even though 11 specs already carry `@pdp`. `qa.yml:135-146` narrows to an area only when *every*
e2e-relevant changed file falls inside that one area's list — a PDP file never does, so `e2e_scope`
falls back to `full`. That is the deliberate fail-safe direction (more tests, not fewer), not a bug —
but it means every PDP PR pays for the whole Playwright suite. Adding an `e2e_pdp` group is a cheap,
self-contained follow-up. **[V]**

### 6d. What a new PDP component is actually required to have

Per `.claude/rules/testing.md` and `.claude/rules/components.md` > Storybook **[V]**:

| Layer | Required? |
|---|---|
| `*.stories.tsx` | **Yes, always**, for anything exported from its folder under `components/` or `pages/`. Not required for a sub-component that only ever renders inside one parent. Needs a `Default` export; named exports for meaningful states only. |
| `play` fn inside the story | Only when there is interactive behaviour worth asserting (validation on blur, disclosure open/close, focus movement, controlled-input wiring). Purely visual stories need none. Query via `within(canvasElement)`, `getByRole` first. Import `userEvent`/`expect` from the Storybook re-export — `pdpProductInfo/index.stories.tsx:2` uses `from 'storybook/test'`. |
| `*.test.ts` (Vitest) | Only when failure would be non-obvious or costly: data mapping, integration boundaries, complex state, pure logic that survives a refactor invisibly. Explicitly **not** for re-exports, one-liners, or framework behaviour. `extractModelLine` is the canonical example of a "yes". |
| `.feature` + Playwright spec | For a new user journey. Gherkin first, **Lead QA signs off the `.feature` before any Playwright is written** (`.claude/skills/qa-generate/`). Tag every `test()` with both `@<area>` and `@SFCC-NNN`. |

Storybook category for PDP components: **`Commerce/`** (`components.md` > Categorisation — "Commerce-specific
shared components"). `Pages/` for the full page assembly. Titles in use today are all consistent with
the rules table **[V]**: `Commerce/PdpProductInfo`, `Pages/PDP`, `Layout/Breadcrumb`,
`Layout/PageToolbar`, `Elements/Button`. Note `zimmPageToolbar`'s story title is `Layout/PageToolbar`
(no `Zimm` prefix) while the component and folder are `ZimmPageToolbar`/`zimmPageToolbar` — follow the
same shape for new ui-kit components.

Accessibility rules are **mechanically enforced** by `.coderabbit/ast-grep-rules/` at PR review:
`<img>` needs `alt`, `IconButton` needs `aria-label`, non-interactive element with `onClick` needs
`role` (+ `tabIndex={0}` + `onKeyDown`). `dangerouslySetInnerHTML` must wrap its value in a sanitizer —
enforced by `semgrep.yml`. `pdpProductInfo/index.tsx:43,54` already does this with
`DOMPurify.sanitize(...)` from `isomorphic-dompurify`. **[V]**

## 7. REUSE OPPORTUNITIES

Things a PDP build should be using rather than rebuilding:

1. **`PdpProductInfo` + its theme recipe** — `overrides/app/components/pdpProductInfo/index.tsx` and
   `overrides/app/theme/components/pdpProductInfo.ts`. Name / price / sanitized description / model
   line / style code, all test-id'd, all styled through `useMultiStyleConfig`. **This is the reference
   implementation of the repo's styling convention** — copy its structure for every new PDP component.
2. **`Breadcrumb`** — `overrides/app/components/breadcrumb/index.tsx`. Wired to live `useCategory`
   data, `aria-label="Breadcrumb"`, `aria-current="page"` on the terminal crumb, `aria-hidden`
   separators, exports its own `BreadcrumbCategory` type. Import it **relatively**.
3. **`ZimmPageToolbar`** — `ui-kits/atoms/zimmPageToolbar/index.tsx`. Already has `recently-viewed`
   and `section-title` variants built and **unused**. A "You May Also Like" / "Recently Viewed" PDP
   section should use `variant="recently-viewed"` rather than a new wrapper.
4. **`extractModelLine`** — `overrides/app/utils/productData.ts`, plus its 5 passing tests.
5. **`ProductWithSizeFit`** — `overrides/app/types/commerce.ts`. Extend this file for new `c_*` fields;
   don't re-derive the Product type per component.
6. **`PDP_OPTIONS_COLUMN_WIDTH`** — exported from `product-detail/index.tsx:14` and already consumed by
   the story. Any gallery/options layout work should import it, not restate `360px`.
7. **`ProductPage` POM** — `e2e/support/pages/ProductPage.js`. Already has `goToProduct()` with the 20s
   SFCC-API gate, `selectVariant()`, `addToCart()`, `getFirstBreadcrumbCategoryLink()`, and locators for
   `product-price` / `product-description` / `product-style-code` / `product-model-info` /
   `sale-price` / `original-price` / `out-of-stock` / `cart-drawer`. **`sale-price`, `original-price`,
   `out-of-stock` and `cart-drawer` locators exist but nothing renders those test-ids yet** — they are a
   pre-agreed contract for the next PDP slice. Use those exact test-ids.
8. **SFCC-91's `pdpColourSwatches`** — 189 lines of component + 256 lines of Vitest + 204 lines of
   stories + an 883-line spec at `.docs/specs/SFCC-91_pdp-colour-swatches.md`, plus the multi-colour
   SKU fixture in `e2e/fixtures/products.js`. **Rebase-and-adopt, do not rewrite.** Two caveats: it
   predates the `pdpProductInfo` theme-recipe refactor (rebase conflict guaranteed in
   `pdpProductInfo/index.tsx`), and it needs relocating to `ui-kits/` + a theme recipe to match convention.
9. **`.claude/rules/overrides.md`** on `origin/feature/f2r-component-registry` — the pre-flight checklist
   (default export, internal-consumer grep, `forwardRef`, Chakra deep-merge audit, prop-superset pattern,
   `vendor.d.ts` ambient rule). If PDP work overrides any SFCC component, run that checklist. Consider
   asking for it to be merged to `develop`, since `overrideStyling.md` already links to it and the link
   is currently dead.
10. **`overrides/app/utils/sfccImage.ts` — `proxyImageUrl(url)`.** **This one matters a lot for the
    gallery.** It rewrites an absolute SFCC static-asset URL to `/mobify/proxy/<path>…` by matching the
    hostname against `getConfig().ssrParameters.proxyConfigs`. Its JSDoc states the reason: direct
    browser access to the Demandware host "is typically blocked by Cloudflare WAF outside of the
    Commerce Cloud network." Any code that renders `product.imageGroups[].images[].link` **must** pass
    it through this helper or images will 403 for real shoppers. It fails open (returns the URL
    unchanged) on a relative or malformed URL. **[V]**

### Gaps the takeover should decide about explicitly

- **The gallery column is a coloured empty box** (`index.tsx:56`). Everything image-related is unbuilt.
- **`overrideStyling.md` vs `uikit-components.md`** — two mutually exclusive styling models on two
  branches (§2c). Get a ruling before writing components.
- **`ui-kits/` has one component and no rules doc on `develop`** (§2b/2c). Both `pdpProductInfo` and
  SFCC-91's `pdpColourSwatches` sit outside it. Either relocate them or stop calling ui-kits settled.
- **The story duplicates the page shell** (`index.stories.tsx:43-65` vs `index.tsx:48-88`) because
  Storybook has no `CommerceApiProvider`. Adding one to `.storybook/preview.tsx` would delete the
  duplication — but `.storybook/` is **Tier 1 frozen** (`frozenFiles.md` > Test & Tooling Config), so
  that needs Integration/SI Partner approval.
- **Error handling diverges from base**: base throws `HTTPNotFound`/`HTTPError` (`index.jsx:194-209`),
  ours renders an inline message (`index.tsx:66`). SEO consequence — a bad `productId` returns HTTP 200
  with an error string instead of a 404. AGENTS.md calls SEO a top requirement; worth raising.
- **`overrides/app/pages/product-detail/` is Squad A territory** (`.claude/rules/squadA.md:5`, draft),
  and the shared product components (`product-tile/`, `display-price/`, `image-gallery/`,
  `swatch-group/`, `recommended-products/`, `product-item/`) are **Tier 2, owned by Squad B**
  (`protectedFiles.md` > Shared Product Components). Overriding any of them crosses a squad boundary
  and needs Squad B notification; AGENTS.md Hard Rule #10 also requires stopping to confirm scope
  before touching more than one protection tier in a change.
