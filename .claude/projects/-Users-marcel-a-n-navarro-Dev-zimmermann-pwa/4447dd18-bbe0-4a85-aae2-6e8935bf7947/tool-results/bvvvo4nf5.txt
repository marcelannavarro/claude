## (a) Verdict

The doc would have prevented most of what is wrong with **how this PR is styled and verified**, and
none of what is wrong with **what it integrates**. Ten material findings map to rules the doc states
plainly and the build broke anyway — the styling layer is authored in the wrong place in two of three
new components, fifteen `var(--zimm-*)` sites sit in JSX where the doc's own chain diagram puts
`textStyle` and semantic tokens, two new numeric-alias-from-a-recipe violations join the five the doc
already lists by name, the `?? ''` empty-element layout void is the doc's §7 pattern (2) verbatim and
is fixed at the call site the doc explicitly says not to fix it at, and the focus ring the doc says
belongs in the recipe is answered two different ways inside one PR and absent from the third. Against
that, the doc is **completely silent** on all three P0s: the Tier 1 `package.json` change, the
`isomorphic-dompurify` module-scope JSDOM evaluation that 500s every SSR request while `tsc`, Vitest,
Storybook a11y and `npm run build` all stay green, and the fact that a page-level override quietly
removes add-to-bag from the storefront. The doc also carries four factual errors that matter here —
its Figma node-type rule is binary and wrong for hug-sized frames, its breakpoint numbers
(768/860/1024) do not exist in this theme, its "settled" `ui-kits` layout does not exist on `develop`
at all, and `recipeGuards.test.ts` — cited three times as the model verification artefact — lives only
on an unmerged branch. Net for the Lead: treat the doc as authoritative on token resolution, styling
layer, and verification discipline; do not treat it as a completeness check for a page override, and
correct §3 and §5 before anyone builds against them.

## (e) DOC GAPS — where the doc is wrong or incomplete, with proposed corrections

**G1 — The Figma node-type discriminator is binary, and that is wrong for hug-sized frames.**
The doc, §5 L227-229: *"**Frames and instances** report a **real box** and are **directly comparable**, so a delta there is a genuine defect."* This investigation found a third case **[F]**: the PDP accordion row FRAMEs report `218 x 9`, which is the **text cap-height of their hugged TEXT child**, not a row height — the real pitch is ≈25.5px. Followed verbatim, the doc turns a correct 25.5px row into a "genuine defect" and someone crushes it to 9px. The doc's supporting heuristic at L231-232 (uniform residual = measurement) would catch it, but it is labelled *supporting* and the primary rule is stated as absolute.
**Correction:** discriminate by **sizing mode**, not node type. A FRAME/INSTANCE with fixed or content-independent sizing (column widths, buttons, icons, the gallery) reports a real box and is comparable; a FRAME that **hugs** a TEXT child inherits the cap-height artifact and is not. For those, measure the **row pitch** (gap + measured offsets), which is artifact-free.

**G2 — The breakpoint numbers do not exist in this theme.**
The doc, §5 L248-249: *"Frames exist at **402 / 1023 / 1440**; breakpoint tokens are **768 / 860 / 1024**."* **[V]** `overrides/app/theme/foundation/gridSystem.ts:8-15` defines `md: '48em'` (768px) and `xl: '80em'` (1280px), with `sm`/`lg`/`2xl` each commented "NOT used". `grep -rn 860 overrides/app/theme/` returns **nothing**. And the PDP page has **no 1023-width frame** — only 402 and 1440 **[F]**.
**Correction:** the active tokens are **768 (`md`) and 1280 (`xl`)**. Keep the rule ("always sweep the bands *between* frames") and drop the numbers, or state them per-surface. For the PDP the undesigned band is 403–1439 and straddles **both** breakpoints — two bands, not one.

**G3 — §3 "Placement, settled" describes an unmerged branch, and the convention is contested.**
The doc, §3 L125-131, calls the layout **settled** and lists `atoms/ zimmButton/ zimmIcon/ zimmLogo/ zimmNavItem/ zimmTextInput/` and `molecules/ zimmInputAction/`. **[V]** `git ls-tree -r develop overrides/app/components/ui-kits/` returns **nothing** — the directory does not exist on `develop`. Those atoms exist only on `feature/SFCC-55_global-footer-ui` (unmerged) and two backup branches. On this branch `ui-kits/` holds exactly `atoms/zimmPageToolbar/` plus a `.gitkeep`. **[V]** No rules file on `develop` states the convention (`ls .claude/rules/` — no `uikit-components.md`); the doc that does state it lives only on `origin/feature/f2r-implementation-workflow` and **contradicts `overrideStyling.md`** — it forbids Chakra inside ui-kit files and mandates per-component `{name}.styles.ts` + Emotion `<Global>`, where `overrideStyling.md` mandates Chakra props plus a theme recipe **[F]**.
**Correction:** replace "settled" with "proposed on `feature/SFCC-55_global-footer-ui`, unmerged, and contested by `.claude/rules/uikit-components.md` on `feature/f2r-implementation-workflow`; `overrideStyling.md` on `develop` is the newer of the two — get a ruling before placing a component." This is live: `pdpProductInfo/` and SFCC-91's `pdpColourSwatches/` both sit **outside** `ui-kits/`, and nobody can currently say whether that is wrong.

**G4 — `recipeGuards.test.ts` does not exist on `develop` or on this branch.**
The doc cites it three times as a live artefact: §2 L102 (*"Intentional merges are allowlisted in `recipeGuards.test.ts`: `Button`, `Header`, `ListMenu`"*), §9 L379-380 (*"**Copy the non-vacuity meta-test.**"*), §10 L448. **[V]** `find . -name "recipeGuards*" -not -path "./node_modules/*"` returns nothing; scanning every branch, it exists only on `feature/SFCC-55_global-footer-ui` and two backups.
**Correction:** mark it branch-local, or the doc's own §10 ("Signposts in the repo that point at nothing") acquires three entries of its own. The *pattern* it teaches is still worth copying — the artefact just is not there to copy from.

**G5 — `generateRegistry.mjs` scan scope is overstated.**
The doc, §3 L134: *"Being under `components/` is load-bearing: `generateRegistry.mjs` only scans that directory."* **[V]** It scans four: `scripts/generateRegistry.mjs:5` — "Scans components, hooks, utils, and pages under overrides/app/" — with walkers at `:649` (components), `:727` (hooks), plus utils and pages. This is why `overrides/app/utils/productData.ts` and `overrides/app/pages/product-detail/` both appear in the generated registry.
**Correction:** "being under one of `components/`, `hooks/`, `utils/`, `pages/` is load-bearing."

**G6 — Wrong line number on a worked example.**
The doc cites `components/header/index.tsx:302` twice (§1 L54, §10 L448) for the dead `fontSize="l"`. **[V]** On this branch it is at **`overrides/app/components/header/index.tsx:293`**. Trivial, but it is the doc's headline live-bug example.

**G7 — No coverage of a build-passes / server-crashes failure class.**
§9's "gap no tool covers" (L425-428) is scoped to **layout** defects. This PR exposes a different one **[V]**: `node_modules/isomorphic-dompurify/dist/index.mjs:3-5` runs `var window = new JSDOM("<!DOCTYPE html>").window;` at **module-evaluation time**, and `overrides/app/components/pdpProductInfo/index.tsx:2` imports it at module scope on a page-reachable path. `npx tsc --noEmit`, `npx vitest run` (146/146), Storybook a11y (27/27) and `npm run build` all pass **[F]**; every `/product/*` SSR request then throws `ReferenceError: Cannot access '__WEBPACK_DEFAULT_EXPORT__' before initialization` **[F]**. I verified the module-scope side effect directly; I did not reproduce the TDZ error.
**Correction:** add to §9 — *"A green build is not evidence the server can evaluate the module graph. Before calling a page done, render its route server-side (dev server or the MRT preview). And before importing a new runtime dependency at module scope, read its node entry (`exports['.'].node.import`) for module-scope side effects — an `import` that constructs a DOM, opens a handle, or reads config at evaluation time belongs behind a lazy call, not at the top of a component."*

**G8 — Bundle budgets: the doc says the wrong thing and omits the headroom rule.**
§9 L411-413 mentions only *"any CSS bundle budget"* and *"`bundlesize` does not run on PRs to `develop`."* **[F]** Reality: `npm run test:max-file-size` enforces `main.js ≤ 180 kB` / `vendor.js ≤ 550 kB` and runs in the **Test-tier gate** (`.claude/rules/tagging.md` § The Test gate), not on develop PRs — so the doc is right about PRs and silent about the gate that does exist downstream. On this branch the measured result is `main.js` 103.46 kB and **`vendor.js` 524.74 kB = 95.4% of budget, ~25 kB headroom** **[F]**.
**Correction:** name the JS budgets and where they actually run, and add *"read the headroom, not the pass/fail — a pass at 95% of budget is a warning that the next dependency will fail the Test gate, on someone else's PR."*

**G9 — §4's intercept model is missing the page/route case, and its grep has a blind spot.**
§4 lists three ways an override silently fails to take effect; all three are component-level, and the prescribed check (L202-208) greps only for **package-specifier** imports. Two additions, both verified:
- **(4th case) Route order beats module resolution for pages.** `overrides/app/routes.tsx:38-40` registers `/product/:productId` **before** `..._routes` at `:41` **[V]**, so the override wins the route match with no resolver involvement at all.
- **The §4 grep misses base-internal relative imports.** Base `node_modules/@salesforce/retail-react-app/app/routes.jsx:43` is `loadable(() => import('./pages/product-detail'))` **[V]** — a relative specifier. `OverridesResolverPlugin.isFromExtends` (`node_modules/@salesforce/pwa-kit-dev/configs/webpack/overrides-plugin.js:128-146`) requires the request to begin with the `extends` package name, so it does **not** rewrite it **[V]**.

> **This also corrects the consolidated findings.** P0-A claims "two independent shadowing mechanisms, so deleting the route entry does not fix it." On the evidence there is **one**. I verified it against the built output: `build/pages-product-detail.js` contains string literals from **both** modules — `product-details-page`, `sf-product-detail-page`, `ZimmPdpProductInfo` (override) *and* `product_detail.recommended_products.title.complete_set`, `useServerContext`, `HTTPNotFound` (base) **[V]** — i.e. both were bundled under one auto-derived chunk name because both import paths spell `./pages/product-detail`. The base module is still there and still wired to the base route inside `..._routes`. **Removing `overrides/app/routes.tsx:38-40` should hand `/product/:productId` back to the base page.** For completeness I also confirmed nothing in the base imports the PDP by package specifier — the only reference is that one relative `import()` **[V]**. This does not soften the finding (merging as-is still removes add-to-bag) but it changes the remediation from "restructure the override" to "one route entry", which is worth knowing before scoping.
> By contrast, the breadcrumb case is the opposite and the findings have it right: both base consumers import by **specifier**, so the resolver does redirect them, and the PLP really is restyled **[V]**.

**Correction:** add the fourth case, and note the grep is specifier-only — *"for a page override, also read `node_modules/@salesforce/retail-react-app/app/routes.jsx`, and check your own `overrides/app/routes.tsx` ordering. And before overriding a page, diff its capability surface against the base — the resolver has no opinion about functionality you dropped."*

**G10 — §7's shared href guard does not exist.**
§7 L326-328 prescribes *"Any href from CMS or fixture data goes through the shared guard"* and ships the implementation. **[V]** `SAFE_HREF` / `isSafeHref` / `safeHref` return nothing under `overrides/` on HEAD **or** `develop`.
**Correction:** same treatment as G4 — mark it branch-local, or reword to "build this when you first need it," because as written it is a signpost pointing at nothing.
