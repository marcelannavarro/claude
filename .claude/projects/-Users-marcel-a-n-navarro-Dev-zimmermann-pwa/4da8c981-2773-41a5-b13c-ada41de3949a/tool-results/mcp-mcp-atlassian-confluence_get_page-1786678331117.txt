Problem Statement</h2><h3 local-id=\\\"b26a4cdffdc6\\\">1.1 Context</h3><p local-id=\\\"04f2c59cc5de\\\">The storefront runs on Salesforce Managed Runtime (MRT), where a Node/Express layer performs all server-side work: the SSR render, proxying to upstream APIs, token exchange, and server-side calls to integrated systems. That layer currently serves three server-side touchpoints: SLAS token validation, payment method metadata, and Marketing Cloud email. Only the first two are Zimmermann integrations. The third is inherited PWA Kit scaffold for SLAS passwordless login and password reset, and Zimmermann does not use Salesforce Marketing Cloud (§5.2). Two proxy origins are configured, SCAPI and OCAPI. Of the 18 external systems in <code>.docs/integration/</code>, <strong>7 are MRT-mediated</strong> and therefore in scope for this decision: SCAPI, Contentful, MuleSoft, GiveX, Booxi, Google Places and reCAPTCHA. The other 11 are browser-direct and never reach the Node layer. Integration build-out begins in the coming sprints.</p><h3 local-id=\\\"c99ff917baaf\\\">1.2 Problem</h3><p local-id=\\\"e3c8406cfc2d\\\">How many MRT applications the storefront deploys, and how integration code is divided across them, has never been decided. The current arrangement is a default inherited from the PWA Kit scaffold, not a deliberate choice, and it has never been documented or signed off. Because deployment topology determines how code is packaged, deployed, and rolled back, it becomes progressively more expensive to change once integration code exists across many systems.</p><p local-id=\\\"e1b468657c04\\\">Compounding this, the safeguards that would contain a failing integration are largely absent. Node's <code>fetch</code> does isolate connections per upstream origin by default, so one slow integration does not starve another's connections. What is missing sits above that layer: per-origin connection limits and response timeouts are unset, integration modules do not consistently catch their own failures, and three route handlers start work whose outcome nothing observes. Seven per-origin connection pools were written to address part of this (<code>overrides/app/ssr/connectionPools.ts</code>) but are imported nowhere and attached to no request. All of this is present-state fact, verified in code, and for the in-process failure behaviours by test (§6), not a projection.</p><h3 local-id=\\\"0cb0bea74c16\\\">1.3 Impact if Not Solved</h3><ul local-id=\\\"90105fdc451c\\\"><li local-id=\\\"3b8f560bda30\\\"><p local-id=\\\"336a54c8c588\\\">Topology is set by accretion rather than decision. Each integration that lands without an agreed position makes the arrangement harder to change, and the decision is effectively made by whoever writes the first proxy.</p></li><li local-id=\\\"3c1f43d09445\\\"><p local-id=\\\"9540a4880219\\\">The missing error handling persists and compounds. It was found by chance in one of the only three server-side touchpoints that exist today, and nothing in the codebase, review process, or CI prevents the same pattern recurring as the remaining MRT-mediated systems are built.</p></li><li local-id=\\\"b2661fd5ebcb\\\"><p local-id=\\\"74f95c30ca13\\\">Deploy and rollback blast radius stays coupled: a bad change to one integration forces a rollback that also reverts every other integration shipped in the same bundle.</p></li><li local-id=\\\"cd86efe06f29\\\"><p local-id=\\\"d27f25226668\\\">Squad A (FED) and the SFCC squad have no shared written position to build against, risking divergent assumptions about where integration code belongs.</p></li></ul><h3 local-id=\\\"bfe0a45e78b2\\\">1.4 Success Criteria</h3><ol local-id=\\\"282880946b92\\\" start=\\\"1\\\"><li local-id=\\\"2a34782637d2\\\"><p local-id=\\\"f3a4993826e5\\\">A single documented position on how many MRT applications the storefront deploys and how integration code is divided across them, signed off by the Technical Lead (§8).</p></li><li local-id=\\\"4b94bd09bf9c\\\"><p local-id=\\\"7fec99357a97\\\">The as-is baseline is verified against the live platform and the codebase rather than assumed, with any inaccuracies in existing documentation identified and raised for correction (§7).</p></li><li local-id=\\\"4a56dd1ccb50\\\"><p local-id=\\\"5bec4f3c1ae9\\\">The present failure behaviour is demonstrated by reproducible automated tests rather than asserted. All integration code (proxy routes, token exchange, server-side API calls) lives inside that single Express application, organised as separate modules. It satisfies every constraint in §2 by construction, because it is the model the platform is built around: one bundle per environment, one hostname per environment, one shared session context across all 8 path-prefixed storefronts. Its weakness is that isolation between integrations is a matter of code discipline rather than infrastructure, and must be built deliberately (§5).</p><h4 local-id=\\\"e7db4dd0e7c1\\\">Option B: Dedicated MRT application per integration / domain <em>(Not viable)</em></h4><p local-id=\\\"f27e69b51566\\\">The proposal was that each integration, or each domain grouping of integrations, would be deployed as its own Managed Runtime application, giving each one an independent process, deploy lineage, and credential scope. This was explored in full rather than dismissed, because on paper it addresses precisely the weaknesses of Option A identified above, and because the question was raised specifically to be settled with evidence rather than assumption.</p><p local-id=\\\"4c51cedae39d\\\">It is not viable, for a reason that is architectural rather than a matter of configuration or budget: <strong>MRT will not host it.</strong> Managed Runtime is documented as supporting only applications created from a PWA Kit template, a full React + Express + PWA Kit storefront bundle, and is not a general-purpose Node or microservice hosting platform. An integration's backend cannot be packaged as an MRT application because it is not a storefront. This was confirmed from three independent directions. First, the platform documentation's own constraint statement. Second, Salesforce's own B2C Commerce Headless Integration guidance for partners, which states that every Composable Storefront must have a project created in Runtime Admin and offers exactly three delivery shapes for backend integration logic (an SFCC cartridge, a Node module extending the same PWA Kit server, or an externally-hosted API) with no fourth pattern of a sibling MRT application. Third, firsthand in Runtime Admin: the Create-a-New-Project flow asks only for a name, a project ID, and two environment defaults. There is no application-type field, because the platform assumes every project is a storefront.</p><p local-id=\\\"45fb6ead9a39\\\">MRT's genuine multi-project support exists for a different purpose: separating distinct brands or domains, each of which is itself a full storefront, not decomposing one storefront's backend. Even setting the hosting constraint aside, three of Option B's consequences would independently count against it: the literal per-integration form breaches the organisation environment cap; every cross-application call would add a network hop to the SSR path that the LCP budget cannot absorb; and the hostname-per-environment binding is incompatible with the single-domain session model the eight storefronts depend on.</p><p local-id=\\\"1b816c280c67\\\">The isolation goals behind Option B remain legitimate. They are addressed within Option A in §5, and the one case Option A genuinely cannot serve is recorded as a risk in §7.</p><hr data-layout=\\\"wide\\\" data-width=\\\"760\\\" local-id=\\\"4a97468367c4\\\"/><h2 local-id=\\\"ac62d051c39a\\\">4. Recommended Option &amp; Rationale</h2><h3 local-id=\\\"e120126a2da2\\\">4.1 Recommended Option</h3><p local-id=\\\"0f4173b50bb8\\\"><strong>Option A: Single MRT application, with per-integration safeguards in the server-side layer.</strong></p><h3 local-id=\\\"77aa4e98f42c\\\">4.2 Rationale</h3><p local-id=\\\"374ac507f13f\\\">Option A is recommended because Option B is not available. The decisive factor is not a trade-off between the two but a platform constraint: MRT hosts only PWA Kit storefront bundles, so an integration cannot be deployed as its own MRT application at all. Once that is established, Option A is the only option that satisfies the §2 constraints, and it satisfies them without migration cost because it is the current state.</p><p local-id=\\\"ab92015d731e\\\">The recommendation is qualified in one important respect. Endorsing Option A is not an endorsement of the status quo, because the status quo includes gaps that are real and demonstrated: integration modules do not consistently catch their own failures, three route handlers leave work unobserved, and no upstream call carries a timeout short enough to fail before MRT's own execution ceiling does. Option A is therefore recommended <strong>with safeguards</strong>: one bundle, but with each integration confined to its own module, given its own connection pool with an independent connection cap and timeout budget, wrapped in its own error boundary, and with every route registration observing the promise it starts. These are specified in §5. Adopting Option A without them would settle the topology question while leaving the isolation gap open, which is the state this document exists to close.</p><h3 local-id=\\\"3fc6dc5d3deb\\\">4.3 Trade-offs Accepted</h3><ul local-id=\\\"8191137a8166\\\"><li local-id=\\\"9fab8abaca5a\\\"><p local-id=\\\"80796f438cfc\\\"><strong>Shared-process failure modes remain.</strong> Even fully implemented, in-process module boundaries do not give memory, event-loop, or crash isolation. A synchronous CPU-bound operation in any integration will block every other concurrent request on that process, and no connection pool or configuration prevents it (demonstrated, §6). This is mitigated by a coding rule, not by infrastructure, and is accepted as a permanent property of the chosen topology.</p></li><li local-id=\\\"86d6f6eee222\\\"><p local-id=\\\"2924b80c501d\\\"><strong>Coupled deploy and rollback granularity.</strong> One immutable bundle per environment means the unit of deploy and rollback is the whole application. A rollback triggered by one integration reverts every integration in that bundle. Accepted; mitigated only by release discipline and small changes.</p></li><li local-id=\\\"9f7775ff656c\\\"><p local-id=\\\"3345d819bf00\\\"><strong>Coarse credential and access scoping.</strong> All integrations' credentials share one flat environment-variable namespace per environment, and MRT project roles are all-or-nothing: anyone who needs deploy or variable access for one integration necessarily has it for all of them. The platform provides no way to scope either within a single project. Accepted; revisit if the team composition changes such that per-integration scoping becomes necessary.</p></li><li local-id=\\\"330b7ae21af4\\\"><p local-id=\\\"e79d7438cf5d\\\"><strong>Isolation depends on convention.</strong> Nothing in the platform or the current CI setup enforces the module boundaries in §5. Accepted, with the mitigation in §7.</p></li></ul><hr data-layout=\\\"wide\\\" data-width=\\\"760\\\" local-id=\\\"a0f0800320d7\\\"/><h2 local-id=\\\"6a6effbdb091\\\">5. All outbound calls pass their own dispatcher.\\nconst response = await fetch(url, {\\n  method: 'POST',\\n  headers: { /* ... */ },\\n  body: JSON.stringify(payload),\\n  dispatcher: mulesoftPool, // per-integration connection cap + timeouts\\n});\\n\\n// 2. Those caps are derived from expected rather than observed concurrency and should be validated by the Stage load-test pass described in §9.3 of that document.</p><p local-id=\\\"ca1f31f5c0c3\\\"><strong>What the pools add.</strong> Node's <code>fetch</code> already creates a separate connection pool per upstream origin by default: it is backed by <code>undici</code>, whose <code>Agent</code> keys one <code>Pool</code> per origin. (Confirmed empirically against the Node 24 runtime rather than by reading a bundled copy, since Node's internal <code>undici</code> is not the one resolvable in <code>node_modules</code>.) A slow integration therefore does not starve an unrelated one, and that is not what explicit pools are for. What the default does <strong>not</strong> provide is a bound on how many connections a single origin may open, or a response timeout short enough to fail before MRT's execution ceiling. Explicit pools add exactly those two things: a <strong>bound</strong> per origin, so one integration under load cannot consume unbounded sockets or overwhelm its upstream, and a <strong>timeout</strong> that lets the integration fail cleanly and return an error rather than the platform terminating the whole request.</p><h3 local-id=\\\"b7ba1e15c514\\\">5.4 Error Handling &amp; Edge Cases</h3><table ac:local-id=\\\"e8e2c9e30168\\\" data-layout=\\\"center\\\" data-table-width=\\\"1360\\\"><colgroup><col style=\\\"width: 453.0px;\\\"/><col style=\\\"width: 780.0px;\\\"/><col style=\\\"width: 126.0px;\\\"/></colgroup><tbody><tr ac:local-id=\\\"d2912c1d96e7\\\"><th ac:local-id=\\\"82100a6066ad\\\"><p local-id=\\\"2fd0dc502470\\\">Scenario</p></th><th ac:local-id=\\\"e010b4ba84cb\\\"><p local-id=\\\"2439a75c9953\\\">Expected Behaviour</p></th><th ac:local-id=\\\"558a3593ab92\\\"><p local-id=\\\"3d9de30bbde2\\\">Type</p></th></tr><tr ac:local-id=\\\"cdf590fcec55\\\"><td ac:local-id=\\\"70d28c1bddcf\\\"><p local-id=\\\"d96823fad502\\\">An integration's upstream returns a non-OK status</p></td><td ac:local-id=\\\"34eb7c6a4e84\\\"><p local-id=\\\"14819c0ccc36\\\">The owning module catches it and returns an explicit error outcome. The §5 implementation does, and it is concentrated in two places. First, attaching a <code>dispatcher</code> to existing <code>fetch</code> calls changes connection behaviour for SLAS token validation and payment metadata, both on authentication and checkout paths, so a mis-set cap or timeout would surface as intermittent failures there rather than as an obvious break. The three tests above cover the failure-isolation behaviour but not cap or timeout tuning, which is why the load-test row is listed as required. Second, <code>overrides/app/ssr.js</code> is the entry point for every request, so the route-handler change must be verified across all 8 storefronts rather than one. One factor usefully bounds the blast radius of both: a <code>dispatcher</code> is passed per call site, so only the two SSR <code>fetch</code> calls listed in §5.2 change behaviour. Everything else, including all commerce traffic issued through <code>commerce-sdk-react</code>, is untouched by definition.</p><hr data-layout=\\\"wide\\\" data-width=\\\"760\\\" local-id=\\\"91c3d4297e10\\\"/><h2 local-id=\\\"2f6c61e7f1f4\\\">7.
