    31	
    32	**Client-mandated:** **LCP ≤ 2s** at p75 mobile, plus Lighthouse Performance ≥ 0.80, Accessibility ≥ 0.90, Best Practices ≥ 0.90. These are the only performance numbers in the signed TSD (§9).
    33	**Other CWV (internal working defaults, not client-mandated):** INP ≤ 200ms · CLS ≤ 0.1. Lighthouse mobile defaults at p75.
    34	**CI gate (SIT gate):** Lighthouse CI (`@lhci/cli`) asserts the Lighthouse score floors above, plus a >5pt trend-drop gate (LHCI server required). SEO intentionally not asserted. Runs on every PR to `develop` ([`digital-sit.yml`](../../.github/workflows/digital-sit.yml)), deploys to the **Dev** tier on merge — treat its numbers as a **regression indicator**, not the contractual measurement.
    35	**Contractual measurement:** Client-mandated LCP and Lighthouse numbers are validated on **Stage** — the prod-mimicking tier (same MRT bundle size class, same CDN/edge configuration, same SFCC realm tier as production). The Dev tier is slower and further from the edge, so its absolute numbers will be worse — that is expected and not a sign-off concern. Full environment topology in [tsd-architecture.md §14.1](./temp/tsd-architecture.md).
    36	**Bundle ceilings — internal CI policy, NOT client requirements:** `main.js` 180 kB · `vendor.js` 250 kB · `main.css` 50 kB (`bundlesize` in `package.json`). (These were set as aspirational targets early in the project. As of the last measurement the actual sizes are well above these ceilings (`main.js` ~352 kB, `vendor.js` ~2 MB) before any optimisation pass — the ceilings need to be re-baselined against measured size + a growth-only headroom (e.g. current + 10–15%) once a baseline pass is done.) Their purpose is regression detection, not a client-facing commitment.
    37	**Third-party script weight:** uncapped — tight LCP is the de-facto constraint. See AGENTS.md > Performance for the deferral rule.

   110	## SSR Requirement (DMU-030)
   111	
   112	Server-side rendering is **mandatory** for product, category, and content pages (DMU-030, signed off). PWA Kit's SSR pipeline must be preserved — do not introduce client-only patterns (e.g. `typeof window !== 'undefined'` short-circuits, client-only data fetching on first paint, or `next/dynamic`-style `{ ssr: false }`) on these page types. Any componentry that cannot render on the server must be gated behind a hydration-safe boundary that still emits SEO-relevant markup on the server.

   114	## Overrides Pattern
   115	
   116	All customizations live in `overrides/` mirroring the structure of `node_modules/@salesforce/retail-react-app/`. Never edit `node_modules/`.
   117	
   118	**Minimise custom code.** When implementing Zimmermann's design and layout, stay as close to the base PWA Kit implementation as possible. Style changes (CSS, Chakra props, theme tokens) are always expected and need no confirmation. Structural changes — restructuring components, altering data flow, or significantly deviating from base template behaviour — must be confirmed with the user before proceeding.
   119	
   120	**Before any change:** check whether the file exists in `overrides/`. If not, create the override:
   121	
   122	1. Copy from `node_modules/@salesforce/retail-react-app/` to the mirrored path in `overrides/`.
   123	2. Rename `.js`/`.jsx` → `.ts`/`.tsx`. Replace `PropTypes` with TypeScript `type` definitions. Add explicit types to all parameters, return values, and props. Use Commerce SDK types (`commerce-sdk-isomorphic`, `@salesforce/commerce-sdk-react`) where available. No `as any` or `// @ts-ignore`.
   124	3. Verify `npx tsc --noEmit` passes with zero errors.
   125	4. **Stop. Present the converted file to the user and wait for approval before making any functional changes.**

   160	## Contentful Content Type Management
   161	
   162	Content types (schema) are never created manually in the Contentful web app. They are
   163	authored in code as one organization-scoped **Environment Template** and installed into
   164	each environment — Contentful's current recommended mechanism, replacing an earlier
   165	per-environment sync pipeline. This makes schema changes reviewable, repeatable, and
   166	team-safe.
   167	
   168	**Key paths:**
   169	
   170	- `scripts/contentful/buildTemplate.js` — assembles every content type in the definitions directory into one `EnvironmentTemplate`, get-or-created by name under `CONTENTFUL_ORGANIZATION_ID`
   171	- `scripts/contentful/setup/installTemplate.mjs` — validates then installs the template's current version into one target environment
   172	- `scripts/contentful/content-types/` — one `.js` file per content type (e.g. `footerConfig.js`), the sole source of truth for its fields (including `localized`/`required`/`validations`)
   173	
   174	**To register a new content type:**
   175	
   176	1. Add a definition file to `scripts/contentful/content-types/<contentTypeId>.js` (see existing files for shape)
   177	2. Run `npm run sync:contentful`
   178	3. Run `npm run install:contentful -- --target <env>` for each environment in the promotion chain
   179	
   180	**To run it:**
   181	
   182	```
   183	npm run sync:contentful
   184	npm run install:contentful -- --target dev
   185	```
   186	
   187	Requires `CONTENTFUL_ORGANIZATION_ID` (scope:shared) and `CONTENTFUL_MANAGEMENT_TOKEN` — a personal token tied to your own Contentful account (scope:personal, never pushed to the centrally-shared GitHub Environments store, but fine to hold locally). Both live in your local, gitignored `.env.shared` (never commit; run `npm run env -- init` to scaffold them, then `npm run env -- <tier>` to activate a tier before running). Get the management token from `app.contentful.com/account/profile/cma_tokens`. `CONTENTFUL_SPACE_ID` is shared across tiers; `CONTENTFUL_ENVIRONMENT_ID` is set per tier and auto-fetched by `npm run env -- init` once the management token is filled in.
   188	
   189	Both scripts are idempotent — safe to re-run. Field deletion during an install is opt-in
   190	(`--delete-deleted-fields` on `install:contentful`), off by default.
   191	
   192	**Relationship to the React component:**
   193	Each content type definition in `scripts/contentful/content-types/` corresponds to a React component in `overrides/app/components/contentful/`. The content type's field IDs must match the TypeScript type in `overrides/app/types/contentful.ts`.
   194	
   195	**Experience Builder components** (drag-and-drop in Contentful Studio) are a separate concern — they are registered in `overrides/app/components/contentful/experiences/definitions.ts` and do not need a corresponding content-type entry unless they also have a standard content type for use outside Studio.

   212	## Integration Map
   213	
   214	All order-creation, fulfilment write, and CRM sync traffic from SFCC routes through MuleSoft as the middleware layer — SFCC does not call NewStore, AP21, Omneo, or Narvar directly. In addition, the PWA's MRT Node layer calls MuleSoft directly for read operations (order history, order details, boutique / BOPIS stock check, real-time stock availability, GiveX balance check) — SFCC is not in those read paths. A handful of services are also called **browser-direct from the PWA** and another set are **SFCC cartridge integrations** invoked server-side. The `Boundary` column makes this explicit so you know where to look when an integration breaks.
   215	
   216	**Boundary key:**
   217	
   218	- **PWA-direct** — called from the browser directly. Vendor key (if any) is publishable/public and safe in the bundle.
   219	- **MRT-mediated** — called from the PWA's Node layer via `/mobify/proxy/` or a server-only endpoint. API credentials held as MRT environment variables; never reach the browser bundle. Includes direct PWA → MuleSoft calls via MRT proxy.
   220	- **SFCC (OOTB)** — Salesforce-bundled integration; no custom cartridge.
   221	- **SFCC (cartridge)** — vendor-supplied or custom server-side cartridge running inside SFCC.
   222	- **SFCC → MuleSoft** — SFCC calls MuleSoft, which fans out to the downstream system.
   223	- **Browser handoff** — PWA hands the user off to a third party's hosted experience.
   224	- **Out-of-band** — no runtime call from PWA or SFCC; the integration delivers data via a separate channel.

   257	## Cross-Storefront Session & Basket Scope
   258	
   259	All eight storefronts are path-prefixed on a single first-party domain and share one SFCC realm with shared customer data. The `httpOnly` SLAS refresh-token cookie set by the SSR layer is therefore presented on every storefront prefix — no cross-domain SSO bridge is needed. SLAS tokens are channel-scoped, so the SSR layer re-initialises the SLAS context per storefront; a registered shopper is silently re-recognised across a storefront switch (shared customer record), while a guest session is site-scoped and does not carry over. **The basket deliberately does not transfer across storefronts** — baskets are site-scoped and priced in the storefront's own currency/pricebook, so a shopper switching storefront starts a fresh basket. Carrying a basket across a currency boundary would produce incorrect pricing. The Global-e checkout handoff is a separate session boundary (Global-e owns its hosted checkout in full). The exact SLAS re-authorisation mechanism and the stay-signed-in UX are open items with the Salesforce integration team.

   261	## Customer Data Migration (DMU-004, updated 2026-05-29)
   262	
   263	Only **email + Omneo customer ID** are migrated into SFCC at go-live. All other customer profile data — name, phone, addresses, communication preferences — is sourced **live from Omneo at login** via MuleSoft. Implication: My Account profile pages cannot rely on SFCC for the full customer record; an Omneo round-trip is required post-authentication. Graceful degradation for Omneo outages becomes load-bearing on account screens. Asset/CDN migration (DMU-010) is **de-scoped** — images stay in Contentful, no asset 301s.

   265	## Blast-Radius Mitigation
   266	
   267	Multiple upstream integrations (SFCC, MuleSoft/Omneo, Global-e, Narvar, Contentful, Didomi, Inside Chat) mean a failure or attack targeting one service must not cascade. A PWA-relevant mitigation can be done in the SSR layer.
   268	
   269	The SSR layer in `overrides/app/ssr.js` uses **Node's native `fetch`**, which is backed by `undici`. Undici's `dispatcher` option (the per-call `dispatcher` option on individual `fetch()` invocations) allows each upstream origin to be given its own connection pool with an independent cap. This prevents a slow or flooded integration (e.g. checkout APIs) from exhausting connections for unrelated origins (e.g. Contentful, JWKS).
   270	
   271	```ts
   272	import { Pool } from 'undici';
   273	
   274	// 1. Create isolated pools for specific origins
   275	const checkoutPool = new Pool('https://api.checkout-service.com', {
   276	  connections: 10, // Hard limit of 10 concurrent connections to this origin
   277	  timeout: 8000,
   278	});
   279	
   280	// 2. Use them explicitly in your fetch calls inside ssr.js
   281	async function getCheckoutMetadata() {
   282	  return await fetch('https://api.checkout-service.com/v1/metadata', {
   283	    dispatcher: checkoutPool, // Safely isolated!
   284	  });
   285	}
   286	```
