## 0. Method and tool caveats (read this before trusting any number)

Two of the four requested tools were **unusable in this session**:

| Tool | Result |
|---|---|
| `get_metadata` (with nodeId) | Works, but the target subtree serialises to >315 KB and the MCP SSE transport truncates it. **Deterministic failure**, retried twice. |
| `get_screenshot` | Works. Used throughout. |
| `get_variable_defs` | **Fails**: `"You currently have nothing selected."` It resolves against the Figma **desktop app's current selection**, not the `nodeId` argument. |
| `get_design_context` | **Fails**: same "nothing selected" error, same reason. |

Because `get_variable_defs` and `get_design_context` were unavailable, all variable, typography and
layout data below was obtained instead via **read-only Plugin API traversal** (`use_figma` with
scripts that only read and `return`). This is a *better* source than `get_design_context` for this
purpose — it returns resolved variable names, collections, modes and per-mode values rather than
pre-rendered Tailwind — but it is a substitution worth stating.

**If you want `get_design_context` / `get_variable_defs` output**, the user must select the node in
the Figma desktop app first; nothing in this environment can do that.

Two further transport quirks, recorded so the next person doesn't rediscover them:
- The SSE channel truncates responses at a **variable** cap (~19 KB–315 KB observed). All traversal
  was paginated.
- **A non-ASCII character in some layer names breaks the SSE JSON encoding outright** (frames named
  `PDP - Denim Applique<U+?>Mini Dress`). Every script below sanitises names to ASCII. A script that
  returns raw `node.name` for that range fails 100% of the time.

### Measurement rules applied

- **TEXT nodes report a cap-height box, not a CSS line box.** Every TEXT height below is labelled
  and must **not** be turned into a CSS `height` or used to file a mismatch.
- **A FRAME that hugs a TEXT child inherits that cap-height artifact.** This bites here: the
  accordion row frames report `218x9`. That 9 px is the text cap-height, not a row height. For those,
  use the **row pitch** (gap + measured offsets), which is artifact-free.
- FRAMEs/INSTANCEs with fixed or content-independent sizing (column widths, button, icons, gallery)
  report real boxes and **are** directly CSS-comparable.

**⚠️ Two genuine typography defects found:**

1. **`body2Strong` letter-spacing is wrong in the repo.** Figma's `Default/Body 2 Medium` is
   **−1% of 14px = −0.14px**. The repo's `body2Strong` uses `letterSpacings.xs` = **−0.12px**. The
   correct existing token is `letterSpacings['2xs']` (`-0.00875rem` = −0.14px), which `linkLg`
   already uses. This is a **varying** residual (other styles match exactly), so per the project's
   own rule it is a real defect, not a measurement artifact.
2. **Product name uses a different style on mobile than desktop** — `Default/Heading 3` (−1% =
   −0.16px) vs `Default/h3-strong` (−0.12px absolute). Same family/size/line-height/case. This is a
   **designer decision to confirm**, not something to silently pick a winner for. The repo has only
   `heading3` (−0.12px), which matches desktop.

### ⚠️ The Desktop/Mobile variable modes are a trap — do not implement them

The design-system `Typography` collection is **mode-switched**, and several sizes differ:

| Variable | Desktop | Mobile |
|---|---|---|
| `default/body-2` | 14 | **12** |
| `default/body-2 medium` | 14 | **12** |
| `default/caption` | 12 | 12 |
| `default/button` | 14 | 14 |
| `line-height/heading-3-medium` | 18 | 18 |
| `line-height/body-2 medium` | 18 | 18 |
| `line-height/caption` | 16 | 16 |
| `line-height/product names` | 16 | 16 |

**But the 402 mobile frame does not switch to the Mobile mode.** Both `3093:67151` (1440) and
`3093:67195` (402) resolve the Typography collection to the *same* mode id (`1226:10`), and no node
in either subtree sets an explicit mode. **Measured consequence: every rendered font size is
identical on both breakpoints (16 / 14 / 12).**

So: implement a **single** type scale. Do **not** add a responsive `fontSize` step for body-2 on the
strength of the mode existing. Whether mobile body text *should* be 12px is an unresolved
**designer question** — the tokens say one thing and the composed screens say another.

### ⚠️ FRAME WIDTH IS NOT A BREAKPOINT

The repo's actual breakpoints (`overrides/app/theme/foundation/gridSystem.ts`, registered in
`theme/index.ts`):

```
base 0em · sm 30em (NOT used) · md 48em = 768px · lg 62em (NOT used) · xl 80em = 1280px · 2xl 96em (NOT used)
```

There is **no 860 or 1024 breakpoint token in the theme** (grepped: zero hits for `860`). If the
brief's "768 / 860 / 1024" came from somewhere else, it is not the Chakra breakpoint scale.

Mapping **402 → `base`** and **1440 → `xl`** is a **decision to be confirmed, not a measured fact.**

**The real gap: the 768–1280 range (`md`) is undesigned for this column.** The design jumps from a
342 px full-bleed mobile block to a fixed 218 px desktop column beside a 900 px gallery. Nothing
specifies what happens in between. Note that the DS `Grid` collection *does* define a Tablet mode
(`grid-columns` 8, `grid-margin` 24, matching the repo's `md` values) — so tablet is tokenised but
not drawn. **This needs a designer answer before implementation.**

### Bonus finding (outside PDP scope, flagged not actioned)

The DS `Grid` collection defines `grid-gutter` = **Desktop 1 / Tablet 24 / Mobile 30**. The repo's
`gridSystem.ts` hardcodes a single `columnGap: '1px'` for all breakpoints and its comment asserts
"1px gutter" at every tier. If `grid-gutter` means column gap, the repo is correct only at desktop.
`gridSystem.ts` is **Tier 1** — do not touch; raise with the UI designer. Columns (10/8/4) and
margins (0/24/30) match the repo exactly.

## 7. TOKEN GAPS — need a UI-designer decision (do not invent values)

Ordered by how likely they are to block implementation.

**A. Off-scale spacing values (6 of them).** `6`, `15`, `22`, `28`, `43`, `44` px are not in the
repo's scale *nor* in the design system's own `Spacing` collection. `28` (the main column rhythm) and
`44` (the largest structural gap) are the important ones. Ask: round to `xl`/`2xl` (24/32) and
`3xl` (40), or add new tokens?

**B. Undesigned tablet (768–1280).** No 1023-ish frame exists. Column behaviour between 342-full-bleed
and 218-fixed is unspecified. Blocking for a responsive implementation.

**C. `#000000` on two labels.** "Size Guide" and "Find your size" use unbound pure black while
everything else uses `text/default` `#191919`. No repo token matches. Almost certainly a design slip.

**D. Product name style differs by breakpoint.** `Default/h3-strong` (−0.12px) desktop vs
`Default/Heading 3` (−0.16px) mobile. Pick one.

**E. `body2Strong` letter-spacing is −0.12px in the repo but −0.14px in Figma.** Unlike the others
this has an unambiguous fix — `letterSpacings['2xs']` already exists and is exactly −0.14px. Still a
Tier 1 file (`typography.ts`), so it needs the designer/owner, but it is a defect not a gap.

**F. Icon sizes with no token.** Accordion chevron `9 x 9` (×4, both breakpoints) and the size
chevron (`9` desktop / `13` mobile). `iconSizes` only has 20/16/12. The 9/13 split between
breakpoints looks unintentional.

**G. Wishlist icon differs by breakpoint** — 16px glyph desktop (in a 24px 4-padded tappable box)
vs bare 20px mobile. Both map to existing tokens, but the mobile one has **no padding**, giving a
20 x 20 hit target — **below the WCAG 2.2 AA 24 x 24 minimum target size (2.5.8)**. Flag to design.

**H. Unbound brand colours.** `#f6f4f1` and `#ffffff` match repo tokens by value but carry no Figma
variable, so they will drift. Cosmetic in the DS, no repo action.

**I. Component dimensions with no token** — gallery `900 x 1170`, swatch `55 x 72` / `56 x 72`,
desktop info column `218`, gallery↔column gap `179`, right pad `142`. Expected for a composed page;
listed for completeness.

**J. The swatch block stays 216 px wide on a 342 px mobile column.** Confirm intentional.
