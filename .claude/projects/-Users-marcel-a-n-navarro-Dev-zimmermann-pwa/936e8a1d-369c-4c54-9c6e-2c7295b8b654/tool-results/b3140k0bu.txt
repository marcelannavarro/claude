The plan doc (`.docs/temp/SFCC-736-195-drawer-tabs-plan.md`, "Fixed — width-clip + overlay bug") documents finding and fixing this *exact* bug on `zimmDrawer/index.tsx` by switching `__css`→`sx` on `DrawerOverlay`/`DrawerContent`. I traced the actual installed `node_modules/@chakra-ui/modal@2.7.0` source to check whether the fix was needed here too:
- `node_modules/@chakra-ui/modal/dist/drawer.mjs` literally re-exports `ModalOverlay as DrawerOverlay` — it is the **same component**, not a lookalike.
- `DrawerContent` (`chunk-JIPYISAW.mjs`) and `ModalContent` (`chunk-6TYU4DP7.mjs`) share byte-for-byte identical prop-spread order: `{..., ...dialogProps, __css: dialogStyles, children}` — the literal `__css: dialogStyles` sits *after* the spread, so Chakra's own internal style wins and the caller's `__css` (which survives inside `dialogProps.__css` via `getDialogProps`'s passthrough, confirmed in `chunk-XG6IELTC.mjs`) is silently discarded.
- `ModalOverlay` has the opposite collision: `{...motionProps, __css: overlayStyle, ref, className, ...rest}` — `...rest` (carrying the caller's `__css`) is spread *last*, so the caller's value wins outright and **replaces** Chakra's own `position:fixed / inset-equivalent / 100vw / 100vh` defaults entirely (plain object-literal semantics, not a merge).
- `zimmModal.css.ts`'s recipe has real, distinct content (`backgroundColor: var(--zimm-color-bg-07)`, `padding: var(--zimm-scale-3xl)`, no default `maxWidth`), and `theme/index.ts`/`theme/components/index.ts` confirm `theme.components.Modal` is **never set by Zimmermann** — only the separately-named `ZimmModal` key is registered.
