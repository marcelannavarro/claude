**🟡 Mega-menu can get stuck open with a phantom "Close" control after a rapid hover→close. PLAUSIBLE, ONE-OFF.**
Traced through `useMegaMenuMotion.ts`'s reducer + `list-menu-popover.tsx`'s `useTransitionSafeValue`:
- `useTransitionSafeValue` (list-menu-popover.tsx:38-57) defers committing a new CSS target value by two `requestAnimationFrame`s, so a genuine prior painted frame exists before the value changes (this is a real, previously-confirmed empirical fix, well documented).
- `useMegaMenuMotion`'s `CLOSE` handler, when `state.phase === 'expanding'`, jumps straight to `{...state, phase: 'collapsing', pendingItemId: null}` (useMegaMenuMotion.ts:65-67) — **keeping `activeItemId`** — specifically to dodge a different, already-guarded stuck-transition bug (contentOut never fading because opacity was never visible). This case *is* covered by an explicit regression test (`useMegaMenuMotion.test.ts:162`, "closing mid-expand collapses directly instead of routing through contentOut").
- But if `CLOSE` fires *before* the original HOVER's deferred double-rAF has committed `value = '1fr'` (i.e., within ~2 animation frames of the hover), `gridTemplateRowsTarget` recomputes to `'0fr'` — which is **already** the current, uncommitted `value`. `setValue('0fr')` is then a no-op (React bails on an identical value), so `grid-template-rows` never actually changes, no CSS transition runs, `onTransitionEnd` never fires, and `COLLAPSE_COMPLETE` is never dispatched. The phase machine is stuck at `'collapsing'` with `activeItemId` still set — so `ListMenuView`'s `useEffect` (list-menu.tsx:59-65) never calls `reportClose()`, and the header shell's `isMegaMenuOpen` stays `true`, keeping `RightBar` on its `'fullSwap'` Close-control (rightBar/index.tsx:175-185) instead of search/icons.
- Real trigger: opening a mega-menu item and closing it (Escape, or `ListMenuTrigger`'s own `onKeyDown` Escape handler at `list-menu-trigger.tsx:72`) within a couple of frames — plausible via a fast Enter-then-Escape keyboard sequence, not just an implausible mouse micro-movement.
- It's self-healing on the *next* hover — the reducer's `HOVER` handler explicitly treats a stuck `'collapsing'` phase as a fresh open (`useMegaMenuMotion.ts:43`) — but in the interim the header shows a stale "Close" control with no visible menu. None of `useMegaMenuMotion.test.ts`'s 14 reducer-only tests exercise this because the bug lives one layer down, in the DOM-timing interaction the reducer tests can't see.

**🟡 `useHeaderNav`'s documented fetch-failure behaviour is wrong, unread, and untested. CONFIRMED, ONE-OFF.**
`overrides/app/hooks/useHeaderNav.ts:45-49`'s `@returns` doc says `items` is `undefined` "on fetch failure... callers should treat that the same as 'nothing to render yet'" — but the type doc four lines above it (line 20-23) and the actual implementation (line 78-82: `items = isLoading ? undefined : resolved ? filterByRegion(...) : []`) agree that `items` is **always `[]`, never `undefined`, once `isLoading` is false** — including on error. Neither `list-menu.tsx:165` nor `drawer-menu/index.tsx:255` ever reads `isError` at all (confirmed by grep — the only non-mock occurrence of `isError` anywhere in the new code is a mocked value in two test files). `useHeaderNav.test.ts`'s 5 tests cover success/empty/locale-fallback but never mock a rejected `getEntries()` call, so this contradiction was never caught. ## Angle 6 — Accessibility

**🔴 SFCC-747 AC10 violated — logo is not the first focusable element. CONFIRMED.**
`header/index.tsx` renders `topBar` (`LeftBar` — hamburger + desktop nav; then `RightBar` — search + icon buttons) at lines 230-251, **before** `logoBar` (the logo button) at lines 256-270. DOM/tab order therefore puts every nav item, the hamburger, the search input, and every icon button *ahead of* the logo. This isn't circumstantial — the PR's own test proves it:
```
overrides/app/components/header/index.test.tsx:107-117
test('is reachable via keyboard Tab order', ...) {
  // The topBar row's own controls (LeftBar's menu-control button, RightBar's close-icon
  // stub — see the mocks above) sit ahead of the logoBar's logo button in DOM order; tab
  // past both first, matching the real component tree.
  await user.tab(); await user.tab(); await user.tab();
  expect(screen.getByRole('button', {name: 'Logo'})).toHaveFocus();
}
```
The test passes *because* it encodes the AC-violating order as correct. The old header (pre-PR) had no such ordering constraint to violate since it wrapped the logo/nav differently — this is this PR's own layout decision.

**🔴 SFCC-747 AC9 violated — logo's accessible name is "Logo," not "Zimmermann, go to homepage." CONFIRMED.**
`header/index.tsx:258-259`:
```tsx
&lt;Button aria-label={t('header.button.assistive_msg.logo', 'Logo')} variant="unstyled" onClick={onLogoClick} __css={styles.logoButton}&gt;
  &lt;ZimmLogo sx={HEADER_LOGO_SX} /&gt;
&lt;/Button&gt;
```
`translations/en-US.json` confirms the shipped fallback is literally `"Logo"`. Because the wrapping `&lt;Button&gt;` carries its own explicit `aria-label`, `ZimmLogo`'s own `aria-label="Zimmermann"` (`zimmLogo/index.tsx:42`, on the inner `role="img"` SVG) is completely superseded in the accessible-name computation — a screen reader announces only "Logo, button," never "Zimmermann" and never the required destination phrase.

**🟡 New nested `&lt;nav&gt;` landmark — regression, not pre-existing. CONFIRMED.**
`header/leftBar/index.tsx:99`: `&lt;chakra.nav __css={styles.nav}&gt;{children}&lt;/chakra.nav&gt;`. At tablet+, `children` resolves to `&lt;ListMenu&gt;`, which renders its own `&lt;nav id="list-menu" aria-label="Main navigation"&gt;` (`list-menu.tsx:77`) — producing `&lt;nav&gt;&lt;nav aria-label="Main navigation"&gt;…&lt;/nav&gt;&lt;/nav&gt;`. The pre-PR header wrapped the identical `children` in a plain `&lt;Box {...styles.bodyContainer}&gt;` (a `&lt;div&gt;`), confirmed via `git show 269d5d4:.../header/index.tsx:236` — so this nested-landmark structure is newly introduced by this PR's `leftBar.css.ts`/`chakra.nav` choice, not inherited.

**🟡 `PopoverFooter onClick` on a non-natively-interactive element with no `role`/keyboard handling of its own. CONFIRMED (rule-letter), likely low practical impact.**
`rightBar/index.tsx:304`: `&lt;PopoverFooter onClick={handleSignout} cursor={isSigningOut ? 'not-allowed' : 'pointer'}&gt;` — `PopoverFooter` isn't natively interactive and has neither `role` nor `tabIndex`/`onKeyDown` of its own, which is exactly what components.md's onClick-on-non-native rule exists to catch. In practice the inner `&lt;Button&gt;` (line 306) is a real, natively keyboard-operable element whose click (mouse or keyboard-triggered) bubbles up to `PopoverFooter`'s handler, so today this likely isn't a live keyboard-trap — but it's a fragile pattern (any future markup change that stops the click event bubbling, e.g. an intermediate wrapper, silently breaks sign-out with no compile-time signal), and it doesn't follow the rule as written.

**Clean:** every new `&lt;Image&gt;` has `alt` (sourced through `resolveImageEntry`'s defensive fallback chain); every new `IconButton` has `aria-label` (spot-checked all ~10); no raw `&lt;div onClick&gt;` pattern anywhere in the new code — every clickable non-button row goes through `ZimmNavItem`, which renders a real `&lt;a&gt;`/`&lt;button&gt;`.
