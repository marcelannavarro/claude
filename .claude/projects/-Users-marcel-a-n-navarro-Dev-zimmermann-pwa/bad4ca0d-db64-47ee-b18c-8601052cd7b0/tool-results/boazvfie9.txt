## 4. Steps

Mechanical gates referenced below, run on every step: `npx tsc --noEmit` clean · `npm run lint` clean · `npm run test` green (this is what runs `recipeGuards.test.ts`'s bare-token + `Zimm*`-namespacing guards, `recipeParts.test.ts`'s parts-vs-reads guard, and `theme/index.test.tsx`'s collision guard) · `npm run audit:tokens` reports no new finding in the touched paths.

Styling rules every step inherits: `textStyle` → `var(--zimm-*)` → recipe → `sx` → `.scss`. Never a bare Chakra key. Never a raw hex/px/rem/em in a component file. Responsive steps are explicit media queries off `breakpoints` imported from `app/theme/foundation` — the pattern `zimmDrawer.css.ts` already uses; do **not** add a third `BP` alias alongside `footerShared.ts`'s and `headerShared.ts`'s. Never Chakra's array shorthand in a recipe.

**Figma space-token mapping:** resolve each `alias/space/NNNN` to the named `--zimm-scale-*` step with the same px value; only seven numeric aliases exist (`025`, `700`, `1100`, `1200`, `1300`, `3500`, `4500`), so verify each against `foundation/spacing.ts` and `foundation/zimmTokens.ts` before typing it rather than inferring from the number. Per §11.10(9), **use the token value, never Figma's decimal** — `12.655` and `8.944` are post-scale render artefacts of `space/1200` (48px) and `space/1000` (40px).

**No hover-reveal surface exists in this bundle** — the cart item's action links are always visible in every Figma frame. If one appears during build, it is `:hover, :has(:focus-visible)`, never `:focus-within`.

### B1 — SFCC-315, cart drawer organism

#### Step 1.1 — Fix `ZimmDrawer`'s `xLarge` width (this is a real bug, not a tidy-up)

**Consequence first.** `zimmDrawer.css.ts` already ships an `xLarge` size whose own comment says it is for Cart. Its value is `WIDTH_XLARGE = '82%'`. Figma's cart panel is a **fixed 1186px** at both 1440 and 1920 (§11.1; panel `x=256` on the 1440 frame and `x=736` on the 1920 frame — 1184 both times, so the *gap* grows and the panel does not). 82% of 1920 is **1574px** — 388px wider than designed. The inner composition is itself fixed (128 + 360 + 140 + 430 + 128 = 1186), so on a 1920 screen the shopper gets 388px of dead white space inside the panel, and the two-column layout sits off-centre. Build SFCC-315 on the existing variant unchanged and it is wrong on every large monitor.

**Mechanism.** The 82% came from a Figma frame annotation, and `zimmDrawer.css.ts`'s own comment records that the *previous* reading of that same annotation was already wrong once ("that frame's annotation was wrong (or superseded)"). The annotation is a percentage; the frames are a fixed width.

**Changes.** Replace `WIDTH_XLARGE = '82%'` with a rem constant equal to 1186px (`74.125rem`), applied as `width`/`maxWidth` with `maxWidth: '100%'` so it cannot exceed a narrow viewport. Keep the comment convention: cite the Figma frames, state that 82% was the annotation and 1186 is the measurement, per the `zimmButton.css.ts` house pattern.

**Pass criteria.**
1. `zimmDrawer.css.test.ts` gains an assertion that `xLarge.content` resolves to the 1186px rem value above `md`, and that `maxWidth` is `100%`.
2. No other size variant's resolved output changes — assert `large`, `tablet`, `small`, `prompt`, `mobile` snapshots are byte-identical to before.
3. `grep -rn "xLarge" overrides/app --include="*.tsx"` returns only `index.tsx`'s type union and `index.stories.tsx` — **confirmed zero production consumers today**, so blast radius is nil. Re-run this before committing; if a consumer has appeared, stop.
4. `npm run audit:tokens` does not flag the new rem constant (it carries a `// audit-allow:` or `provisional` comment naming the Figma frame, matching `PANEL_MIN_NARROW`'s existing treatment in the same file).
