## 1. If this merges tomorrow, here's what breaks

### The headline

The live PDP loses add-to-bag, colour swatches, the quantity picker, recommended products, the
information accordions, wishlist, basket integration, proper 404 status codes, SSR cache headers,
deferred hydration, and all the Einstein / Data Cloud / Active Data analytics.

Not because anything was sabotaged. Because the new page renders three things — a grey box where
the gallery goes, the product info panel, and a breadcrumb — and it takes over the URL that used to
render Salesforce's 876-line page.

### Why it takes over, explained from scratch

PWA Kit has a file-replacement system. Put a file at `overrides/app/pages/foo.tsx` and it stands in
for the base Salesforce file at the same path. That's the whole idea, and it's how everything in
`overrides/` works.

The interesting part is *when* it kicks in. A webpack plugin inspects each import and only redirects
it if the import **names the package** — something like
`@salesforce/retail-react-app/app/components/breadcrumb`. Its own code comment says it plainly:

> *"returns true only if the import request points to a package in 'extends'… If false, the import
> request proceeds to the base package in node_modules"*

Now look at how base Salesforce loads its own PDP:

```js
const ProductDetail = loadable(() => import('./pages/product-detail'), {fallback})
```

That's a **relative** path. No package name. So it is never redirected — base Salesforce keeps
loading its own real page, untouched.

So why does the storefront show the cut-down version? Because of this, in `overrides/app/routes.tsx`:

```js
{
  path: '/product/:productId',
  component: ProductDetail,     // ← the override
},
..._routes,                     // ← base Salesforce's routes, including the real PDP
```

Our route is registered **first**. First match wins. That's the entire mechanism.

**Delete lines 37–40 of `overrides/app/routes.tsx` and the full base PDP is back.** I confirmed both
pages are sitting in the shipped bundle side by side — `build/pages-product-detail.js` contains
markers unique to our override *and* markers unique to the base page, and the same file fetched from
the live preview is byte-for-byte identical to my local build.

**Why this matters for planning:** earlier notes (mine included) said there were *two* mechanisms
doing this and that deleting the route wouldn't help. That was wrong, and it inflated the fix from
four lines to a rewrite. The regression and the delivery are now separate problems, which is a much
better position to be in.

### The breadcrumb is the opposite case, and it really is a problem

Same system, different outcome. Two base Salesforce files import the breadcrumb **by package name**:

- `product-view/index.jsx:45`
- `product-list/partials/page-header.jsx:14`

Package name means the redirect fires. So both of those now get our breadcrumb. The second one is
the **PLP**.

A PDP ticket has silently restyled the product listing page — chevron separator replaced with `/`,
uppercase, the `useStyleConfig('Breadcrumb')` hook orphaned, the `sf-crumb-item` test id gone. Squad
B's page changed appearance with no design review and no notice. Nobody would find this except QA or
a shopper.

There's a second-order oddity worth flagging to Squad B: SFCC-89's AC puts the breadcrumb *below*
the product images. On the PLP, breadcrumbs are top-of-page wayfinding. The same component may not
want the same placement.

## 2. The bigger problem I found by accident

**No page on this storefront is server-rendered. On any route. On any environment I could reach.**

I went looking for the reported PDP crash on the preview environment and found something else: every
URL returns HTTP 200 with the app shell rendered and a **loading spinner** where the page content
should be.

| URL | Result |
|---|---|
| preview `/` | 200, spinner |
| preview `/en-au/product/8637DS241-3` | 200, spinner |
| preview `/en-au/product/DEFINITELY-NOT-A-SKU` | 200, spinner |
| preview `/en-au/category/womens` | 200, spinner |
| preview `/en-au/search?q=dress` | 200, spinner |
| preview `/en-au/login` | 200, spinner |
| **`test` tier `/`** | 200, spinner |
| **`test` tier `/en-au/category/womens`** | 200, spinner |

Supporting detail: the PDP's HTML is identical to the homepage's apart from the canonical URL. Its
`<title>` is `Retail React App` — the fallback, not a product name. The strings `Style Code` and
`Unable to load product information` appear **zero** times in the served HTML. Same output for curl,
for a real Chrome user-agent, and for Googlebot. The shell itself *is* server-rendered — header,
footer, the SVG sprite, the full theme. It's the page components that never arrive.

And the preview genuinely is running this PR's code — the served chunk matches my local build byte
for byte.

**What this costs.** The project brief opens with *"Must be robust and secure and SEO-friendly"* and
sets a ≤2s p75 mobile LCP budget. Client-rendered spinners defeat both. Every "compare the preview
against Figma" review anyone has ever done on this project has been reviewing a client-rendered page.

**My best guess at the cause, stated as a guess.** Every page in base Salesforce's route table is
wrapped in `loadable(() => import(...), {fallback})`. A correct shell plus a spinner in `<main>` is
exactly what you get when the server-side chunk resolution doesn't happen and the `fallback` renders
instead. That points at `ChunkExtractor` / `loadable-stats.json` wiring in `overrides/app/ssr.js`
and `overrides/app/ssr/` — **Tier 1, Integration-owned, and one of the four absolutely-untouchable
files.** Do not go near it. Report it.

**Two things this changes immediately.**

First, it clears the reviewers. The criticism that nobody opened the preview URL doesn't survive:
opening it shows a spinner on the PDP *and* on the homepage, indistinguishable. Any reviewer who
looked would reasonably conclude "previews don't SSR here" and move on. Don't use that as a stick.

Second, the reported PDP crash and this finding are consistent, not contradictory. The crash happens
where SSR actually evaluates the page module — which is where the CI Playwright run served from. On
MRT it's **masked**, because MRT never evaluates the page module server-side at all. Which also
means: **the MRT preview is not a usable SSR smoke test on this project.** Any process fix that says
"hit the preview and check the status code" would have produced a false pass here.

**One gap before you escalate.** I could only reach the preview and the `test` tier — `test`
publishes its URL as an environment variable, `dev` and `sit` don't, and I had no URL for `staging`
or `prod`. Find out whether they behave the same before deciding how loud to be.

## 3. Corrections — including to my own earlier notes

Trust matters more than looking consistent, so these are stated flatly.

### Don't "fix" three of the flagged styling violations — you'd ship a bug

I earlier told you nine `var(--zimm-*)` uses in component files were all violations to move into
theme recipes. **Three of them are correct as written.**

Here's why. Chakra resolves style props against named scales in the theme, but our
`overrides/app/theme/index.ts` only registers six of them: `borderWidths`, `breakpoints`, `colors`,
`fonts`, `space`, `textStyles`. **`sizes` is not registered.** So a bare token key works fine on
`margin` or `padding` (which resolve through `space`) and silently misresolves on `width`, `height`
or `boxSize` (which resolve through `sizes`).

Lines 69–71 of the page are `<Skeleton height="var(--zimm-scale-800)" />` and similar. `height` is
a sizing prop. The raw `var()` is the **only** correct form there. Convert them to bare keys and the
skeletons break.

Worth noting Jhoan got this exactly right — the same lines use `mb="m"` and `mb="xl"`, bare keys on
a *spacing* prop, which is correct. He wasn't guessing.

The revised picture:

| Site | Verdict |
|---|---|
| `product-detail:69, 70, 71` — `Skeleton height` | **Correct. Leave alone.** |
| `product-detail:63` — `pt` 16px | Real violation, `m` exists, safe to move |
| `product-detail:61, 62` (base) — 32px gutter | Real violation, but the right value is **30px**, not the 32px `2xl` token. Use `grid.containerPadding.base`. |
| `product-detail:52` — `columnGap` 180px | Real, but **no named token exists** — our spacing scale tops out at 160px. Designer question. |
| `product-detail:62` (md) — `pr` 140px | Same. Designer question. |
| `breadcrumb:33`, `zimmPageToolbar:58` | **Different problem entirely** — these are motion values, and there's no motion scale to reach for. Import the `motion` constant from `app/theme/foundation`. Heads up: `motion.ts` says its own values are *"PROVISIONAL… Do not treat as final."* |

### I was wrong about the fonts

I told you a Tier 1 governance file was factually wrong about self-hosted fonts. It isn't. On this
branch and on `develop`, `frozenFiles.md` says **"No font binaries in this repo"** and explains that
type renders from the fallback stack — which is correct, and is a licence position, not an oversight.

The "fonts are self-hosted" wording exists only on the SFCC-55 footer branch. **My session started
on that branch**, so the copy of the rules in my context was that branch's version, and it didn't
update when I switched. Practical takeaway for you: anything I quote from `.claude/rules/` is worth
re-checking against the branch actually in hand.

The downstream conclusion survives and still matters: there are no font files, so every local and
preview visual check rendered the fallback face. **No type metric on this PR has ever been visually
validated** — and SFCC-732/733 are the styling ACs that will be QA'd on exactly those metrics.

*Related risk:* if the SFCC-55 branch merges, it brings a `frozenFiles.md` that asserts self-hosted
fonts plus two `.woff2` files — which would contradict the Monotype licence position currently
recorded in that same Tier 1 file. Flag it to whoever owns SFCC-55 before it lands.

### The jsdom / bundle-budget link doesn't exist

Several notes connected the new dependency to `vendor.js` sitting at 95.4% of its budget. There's no
connection. `grep -c jsdom build/vendor.js` returns **0**. The package ships a browser entry point
that doesn't import jsdom at all, and the client build resolves to it. Client-side cost is
`dompurify` alone.

The 95.4% is real and is a standing risk with ~25 kB of headroom — but it's pre-existing and
unrelated. **Raise them separately or the budget concern gets dismissed along with the dependency.**

This also improves the options: because a jsdom-free browser entry exists, "rip the package out"
isn't the only route. See §6.

### SEO needs no new package

An unresolved CodeRabbit thread asks for `react-helmet`, and I'd previously called that a Hard Rule
#7 problem. It isn't — **`react-helmet@6.1.0` is already installed** as a dependency of
`retail-react-app`, and base ships a ready-made `app/components/seo` wrapper. Import that. It's a
published entrypoint, so it satisfies our import rules too.

One thing that comes with it: the base SEO block reads `product.pageTitle` and `pageMetaTags`, and
our `useProduct` call requests no `expand` list at all where base requests nine fields plus
`perPricebook: true`. Restoring SEO means restoring the expand list.

**Which raises a question nobody has asked.** AC-2 wants a single full price. The override reads
`product.price` with no `perPricebook` and no `expand: ['prices']`. I haven't proved that returns
the wrong number — but the base page doesn't trust that field, and neither should we without
checking against live data.

## 4. What this PR gets genuinely right

Read this before §5, because the calibration matters.

**The component and its theme recipe are the best worked example of our styling pattern anywhere in
this repo.** `ZimmPdpProductInfo` is correctly namespaced so `extendTheme` has nothing to merge into.
It's registered properly. All five of its parts are actually consumed — not a registered-but-unread
recipe. The two escape hatches it needs are exported *from the theme file* and imported by the
component, so even the call-site styling is named where styling belongs, with a written note
explaining what would collapse them and why that's blocked. **Copy this shape for everything else.**

**Zero bare scale keys on any sizing or typography prop, across the entire branch.** This is the
single most dangerous trap in this codebase and the branch is completely clean on it. Given that a
mistake here fails silently, that's not luck.

**The provisional column width was flagged in code as provisional** rather than silently guessed.
The value turned out to be wrong — 218px measured against 360px written — but the *behaviour* was
exactly right, and that distinction is the whole point of the rule.

**Accessibility is asserted, not claimed.** Proper `h1`, `nav[aria-label]`/`ol`/`li`, `aria-current`,
`aria-hidden` on separators, and a Storybook `play` that proves the *negative* case when content is
absent. Storybook a11y is gated at `error` in CI, so those assertions genuinely run.

**Also right:** data fetching lives only in the page, all three components are pure and prop-driven ·
`getTemplateName` retained, easy to drop · a discriminated union for the toolbar props, exactly per
our TypeScript rules · both `dangerouslySetInnerHTML` sites sanitised — the security instinct was
right, only the dependency was wrong · `storybook/test` imported correctly *against* a repo rule that
says otherwise · Storybook categorisation right four times out of four · gherkin-first followed, the
`.feature` file exists · `tsc` clean, Vitest 146/146, Storybook 27/27 · **and every Tier 1 file left
alone** — no workflows, no playwright config, no `.storybook/`, no theme foundation, no `ssr.js`. On
an overdue story with three tempting Tier 1 shortcuts sitting right there, that's discipline.

### Decision 1 — What does the PDP page actually do?

| **(a) Delete the route entry now**, ship the components later | Storefront keeps the full base PDP immediately; regression gone in four lines. But the three new components render nowhere, so SFCC-89 doesn't deliver and slips further. Cheapest safe state. |

Runs straight into our own **Minimal changes** rule — *"Do not remove or replace existing base template functionality unless explicitly instructed"* — so it needs an explicit product instruction recorded on the story, not a reviewer's assumption. |

**My recommendation, as a recommendation:** (a) today, (b) as the delivery path. Splitting them is
only possible because of the correction in §1 — under the old "two mechanisms" reading it wasn't.

Waiting on this: the 218px column, the 30px gutter, the two token gaps, the mobile prose inset

### Decision 3 — The sanitiser and the Tier 1 dependency

| Option | Cost |
|---|---|
| Approve as-is | Needs Integration sign-off, and SSR still crashes wherever SSR works. You'd be approving the defect. Not viable. |

### Decision 4 — How you take the PR over

Two mechanical facts to plan around:

- **`dismiss_stale_reviews` is on.** Every push you make dismisses any approval already given. Batch

- **You could push the Tier 1 change and approve it yourself** — Jhoan is the author, so nothing
  mechanically stops you. Don't. Our own rule says the gate exists *"so a compromised or careless
  session can't grant itself write access to a frozen file,"* and collapsing author and approver

Also: **SFCC-91 (colour swatches) already branched off SFCC-89 at an older commit** and carries ~650
lines plus an 883-line spec. Rebasing it will conflict in the product-info component. **Adopt that
work, don't rewrite it**, and tell Jhoan before you convert anything.
