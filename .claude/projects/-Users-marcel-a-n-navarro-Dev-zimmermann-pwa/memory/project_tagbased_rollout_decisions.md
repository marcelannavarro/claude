## Decisions

- **Q3 — SIT trigger: DECIDED = Option B (2026-08-05).** SIT stays **branch/gate-driven** (`deploy-sit.yml` keeps its `workflow_run`-off-SIT-Gate trigger on `release/**`), **NOT** tag-triggered. Documented as an **intentional exception**. Rationale: SIT is a *continuous auto-integration* tier — same category as **Dev** (which the proposal already keeps non-tag-based) — not a deliberate pinned-promotion tier. The tag model governs the promotion tiers (Test/UAT/Stage/Prod). Keeping B preserves the gate-then-deploy safety guarantee and means **zero `deploy-sit.yml` code change**. Clean two-category model: *continuous auto* = Dev + SIT; *tag-promoted* = Test/UAT/Stage/Prod. **Key clarification for stakeholders:** "using tags" ≠ "being triggered by a tag" — tags/Releases still exist and are visible (cut on the release branch, promoted up UAT/Stage/Prod); SIT simply auto-refreshes rather than waiting for a tag. Optional future escape hatch: add a `workflow_dispatch` tag override to `deploy-sit.yml` if NewStore ever needs to pin a specific `-rc`. Decided by Marcel; formal recording on the Confluence page/topology docs to be done jointly with Tim (don't unilaterally edit Tim's proposal).
- **Q1 — Test-gate design: DECIDED = deploy-then-gate (2026-08-05).** Deploy first (keeps the fast on-demand look), then run the check against the just-deployed build as a 2nd job in `deploy-test.yml`; the run's overall pass/fail = the "safe to promote to SIT" signal. Aligns with Marcel's own review. Test is a fast disposable quick-look tier, so the inconsistency vs SIT's gate-then-deploy is intentional/fine.
- **Q2 — Test-gate scope: DECIDED = P0 Playwright + bundle-size (2026-08-05).** Skip contract-tests (stub, `exit 0`) and Lighthouse (needs LHCI server; trend value doesn't suit disposable Test). Rationale: bundle-size is cheap/deterministic/already-wired and mobile page-speed is a top project priority — catch bloat at the earliest deployed tier. **Diverges from the current proposal draft (P0-only) → needs Tim's nod when synced.** Impl note: bundle-size checks the build artifact, runs alongside P0 in the post-deploy gate job.

- **rc-tag-cutting method (the branch-protection wrinkle): DECIDED = Option 1, tag-only (2026-08-05).** The `release/**` branch protection (require PR, `isAdminEnforced` no-bypass) blocks the proposal's `npm version → push commit to release branch` step, because `npm version` bundles a package.json-bump *commit* with the tag. Resolution: for `-rc` tags, tag an existing release-branch commit and push the **tag only** — `git tag -a v0.1.0-rc.N -m "..." && git push origin v0.1.0-rc.N`. A tag push is not a branch push, so protection doesn't block it, and the **tag ruleset** enforces naming (the real guarantee; `npm version` was only convenience). No per-rc branch commit; `package.json` version bumped once at the final-release PR. Keeps branch protection fully strict AND keeps rc-cutting cheap + open to any dev (matches the proposal's "rc = any developer"). **Rejected Option 2** (add a tier-1 bypass) — opens a standing hole in the no-bypass lock we just set and would restrict rc-cutting to tier-1 only. Deviation from the proposal's literal `npm version` step → flag to Tim.

**ALL DECISIONS NOW SETTLED (2026-08-05): Q1, Q2, Q3, + the tag-cutting wrinkle.** Next phase = build.

## Build findings

- **CRITICAL (2026-08-05): GitHub org plan is `team`, NOT Enterprise → ruleset *metadata* rules (`tag_name_pattern`, `branch_name_pattern`, `commit_*_pattern`) are silently NOT ENFORCED.** Proven empirically: created `tag-rc`/`tag-release` rulesets; a malformed `v9.9-rc.0` push was **allowed** (tag_name_pattern inert) but its **deletion was blocked** (core `deletion` rule enforced). Confirmed `gh api orgs/ZimmermannAU --jq .plan.name` = `team`. **Implication:** rulesets on this plan enforce **creation-restriction + immutability (update/deletion)** — core rules — but **cannot hard-block tag *name format*.** A `push: tags:` validation workflow runs *post-creation* (CI trigger) so it can only flag/fail, not prevent. So on Team plan there is **no server-side hard-block on tag naming** — naming = convention + a local pre-push guard + post-hoc CI alert. Rulesets currently live: `tag-rc` (id 20487306), `tag-release` (id 20487243), both `active`. Side effect learned: a malformed tag that slips in is **immutable/stuck** (can't delete without disabling/deleting the ruleset — admin only). **DECIDED (2026-08-05):** (1) **Keep** the inert `tag_name_pattern` rules (future-proof if org→Enterprise; harmless) — to be **labelled as inert on Team** in the tag docs so nobody's misled. (2) Naming enforcement = **local pre-push hook** (Husky; the only true *prevention*, blocks a bad name before it leaves the dev's machine) + **`push:tags` validation workflow** (post-hoc *detection*/alert). Both **promoted to front-line**, done right after the rulesets — no longer "defense-in-depth."
