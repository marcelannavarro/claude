     1	---
     2	name: code-quality
     3	description: Audit recently changed or specified files for code quality issues — naming, circular imports, TypeScript coverage, test/story existence, and structural debt. Read-only. Use after implementing a feature or before opening a PR.
     4	---
     5	
     6	Audit code quality for the specified scope. Do not modify any files — this is a read-only
     7	diagnostic. Produce a prioritised report with actionable fixes.
     8	
     9	---
    10	
    11	## Input
    12	
    13	The user will provide one of:
    14	- A file path or directory to audit
    15	- No argument — default to files changed on the current branch: `git diff --name-only main`
    16	
    17	If no argument is given, run: `git diff --name-only main` and audit those files.
    18	Exclude test files (`*.test.ts`, `*.spec.ts`), stories (`*.stories.tsx`), and any registry files.
    19	
    20	---
    21	
    22	## Parallel execution
    23	
    24	For audits covering more than 5 files, split into four independent checks and run them
    25	as parallel agents simultaneously. Each agent receives only its own checklist — do not
    26	bundle all checks into one agent.
    27	
    28	- **Agent A — Naming & structure**
    29	- **Agent B — Import analysis**
    30	- **Agent C — TypeScript coverage**
    31	- **Agent D — Test & story coverage**
    32	
    33	For 5 files or fewer, run all checks sequentially in a single pass.
    34	
    35	---
    36	
    37	## Agent A — Naming & structure
    38	
    39	Rules are defined once, split across [.claude/rules/conventions.md](../../rules/conventions.md)
    40	(cross-cutting), [css.md](../../rules/css.md) (Chakra/styling), and
    41	[components.md](../../rules/components.md) (components/hooks/Storybook) — read the relevant
    42	ones first, then apply each rule to the files in scope. Do not re-list the rules here;
    43	that's how the files drift apart.
    44	
    45	Walk the file list and audit each file against the relevant section:
    46	
    47	- Every file → conventions.md **General** section.
    48	- Every file with JSX/Chakra props → css.md **Tokens** section (no hardcoded hex/px values).
    49	- `.tsx` under `overrides/app/components/` or `overrides/app/pages/` → components.md
    50	  **Components** + **Composition** sections, plus conventions.md **File naming and folder
    51	  structure**.
    52	- `.ts` under `overrides/app/hooks/` → components.md **Hooks** section.
    53	- `.ts` under `overrides/app/utils/` → conventions.md **Utilities** section.
    54	
    55	For each violation, record `file:line` and which rule file + bullet failed — the section
    56	anchor is enough (e.g. "components.md → Components → Props type placement").
    57	
    58	---
    59	
    60	## Agent B — Import analysis
    61	
    62	For each file, read the import statements and check:
    63	
    64	- No circular imports: if File A imports from File B, File B must not import from File A
    65	  (check by reading the imported file's imports in turn — one level deep is sufficient).
    66	- No imports from a higher tier without justification:
    67	  - A component must not import directly from internal `commerce-sdk-react` source paths.
    68	  - A page must not bypass its own hooks to call raw API functions.
    69	- No imports from a later-sprint feature (reference `.docs/memory/sprintScope.md` when present).
    70	- No `../../../..` chains longer than 3 levels — flag for path alias review.
    71	
    72	---
    73	
    74	## Agent C — TypeScript coverage
    75	
    76	Check each file against the relevant rule file:
    77	
    78	- Every `.ts`/`.tsx` → [typescript.md](../../rules/typescript.md) in full (no `any` without
    79	  justification, `type` vs `interface`, non-null assertions, discriminated unions, utility
    80	  types, `import type`, `satisfies`, `readonly`, generic naming).
    81	- Components → [components.md](../../rules/components.md) **Components** (props type name,
    82	  placement, optional `?`, callback naming, JSDoc).
    83	- Hooks → [components.md](../../rules/components.md) **Hooks** (typed params, explicit
    84	  return type, JSDoc with `@returns`).
    85	
    86	Then run `npx tsc --noEmit` **once** for the whole branch (not per file) and report any
    87	errors. Cross-reference any new errors against the files in scope.
    88	
    89	---
    90	
    91	## Agent D — Test & story coverage
    92	
    93	For each component file under `overrides/app/components/` or `overrides/app/pages/`:
    94	- A paired `*.stories.tsx` exists in the same directory (required by [AGENTS.md](../../../AGENTS.md) > Testing).
    95	- For logic-heavy components or hooks: the component's **own** `*.test.ts`/`*.test.tsx` exists
    96	  in the same folder. A `play` function elsewhere (this component's own story, or — this is
    97	  the common miss — a *different* component's assembly-level story) does not substitute for
    98	  it, even when it happens to exercise the same rendered output; see testing.md's note under
    99	  "What to test (and what to skip)". A component's own test file may still mock a hook or
   100	  child component whose internals are covered elsewhere — the point is that the component's
   101	  own render-branch/event-wiring contract has a test discoverable from its own folder.
   102	- If a test file exists, verify:
   103	  - At least one test covers the primary render case.
   104	  - At least one test covers a user interaction (click, input) if the component has interactive elements.
   105	  - No tests use `toBeTruthy()` as the sole assertion — check for meaningful assertions.
   106	- If a paired `.stories.tsx` is missing, flag as MISSING STORY (mandatory).
   107	- If a logic-heavy file has no test file of its own, flag as MISSING TEST — regardless of
   108	  whether a `play` function exists somewhere else in the codebase.
   109	
   110	For each utility file under `overrides/app/utils/`:
   111	- **`.test.ts` required** when the utility has ≥1 conditional branch or performs ≥1
   112	  transformation (currency, locale, mapping, parsing, etc.). Trivial re-exports and
   113	  one-liners are exempt.
   114	- If a test file exists, verify it covers both the happy path and at least one edge case
   115	  (empty input, null, locale variation — whichever applies).
   116	
   117	---
   118	
   119	## Output format
   120	
   121	Combine all agent results into a single prioritised report:
   122	
   123	```
   124	## Code Quality Report
   125	**Scope:** [files audited]
   126	**Branch:** [current branch]
   127	**Date:** [today]
   128	
   129	### 🔴 Must fix before PR merge
   130	[Issues that would fail review or cause runtime errors — one line per issue with file:line]
   131	
   132	### 🟡 Should fix in this PR
   133	[Issues that affect maintainability or violate conventions — one line per issue with file:line]
   134	
   135	### 🔵 Backlog (log, don't block)
   136	[Minor style issues, missing test cases for edge cases — one line per issue]
   137	
   138	### ✅ No issues found
   139	[List checks that passed cleanly]
   140	
   141	### Summary
   142	X must-fix · Y should-fix · Z backlog items
   143	```
   144	
   145	Do not suggest refactors beyond the scope of the changed files.
   146	Do not modify any files — report only.

     1	---
     2	name: qa-generate
     3	description: Generate a Gherkin .feature file and Playwright test spec from a Jira story. Human-in-the-lead — Lead QA validates the .feature before Playwright is generated. Use for any new storefront user journey that needs E2E test coverage.
     4	---
     5	
     6	QA test generation is a two-step, human-gated process. Do not generate the Playwright spec
     7	until the `.feature` file has been explicitly confirmed by Lead QA.
     8	
     9	> **Three testing layers in this project** (per [AGENTS.md](../../../AGENTS.md)):
    10	> - Vitest — unit logic
    11	> - Storybook `play` functions — component interactions
    12	> - Playwright — E2E user journeys (this skill)
    13	>
    14	> The gherkin → Playwright workflow below is the **E2E layer only**. It does not replace
    15	> the Vitest / Storybook layers — write all three where each applies.
    16	
    17	> **Status:** the `e2e/` directory and Playwright harness must be in place before running this skill.
    18	> If `e2e/` does not yet exist, stop and tell the developer the QA harness must land first.
    19	
    20	---
    21	
    22	## Phase 1 — Gather story details
    23	
    24	Ask these questions one at a time. Wait for the answer before asking the next.
    25	
    26	1. What is the Jira story key? (e.g. SFCC-142)
    27	2. What is the story title?
    28	3. What are the acceptance criteria? (paste them directly)
    29	4. Which squad owns this story? (Squad A: checkout/cart/payments — Squad B: PDP/PLP/search/account)
    30	5. Which sprint is this? (Check `.docs/memory/sprintScope.md` — flag if the story references a later-sprint dependency)
    31	6. Is this a P0 journey? (P0 = Digital SIT gate critical path: guest checkout, registered checkout, PDP variant selection, ATC, auth)
    32	
    33	---
    34	
    35	## Phase 2 — Draft the .feature file
    36	
    37	Write the Gherkin file to:
    38	`e2e/features/{area}/{JIRA-KEY}_{short-description}.feature`
    39	
    40	Follow the standard in `e2e/features/README.md`:
    41	- Tags: `@{JIRA-KEY} @{area}` — add `@p0` if confirmed in Phase 1
    42	- Feature block with persona, goal, and value
    43	- Background block for shared preconditions
    44	- At least one happy path scenario and one failure/edge scenario
    45	- Plain English only — no selectors, URLs, or implementation detail
    46	- Under 150 lines — split by scenario group if longer
    47	
    48	**Stop here. Do not generate the Playwright test yet.**
    49	
    50	Present the draft and say:
    51	> "This is the draft `.feature` file. Please share it with Lead QA for validation.
    52	> When QA has approved or annotated it, reply with their feedback and I will proceed."
    53	
    54	---
    55	
    56	## Phase 3 — Apply QA annotations (if any)
    57	
    58	If Lead QA returns annotations in this format:
    59	```
    60	# QA ANNOTATION: [correction]
    61	```
    62	
    63	Update the `.feature` file to reflect the correction. Confirm the change explicitly:
    64	> "Updated [what changed]. No other changes made."
    65	
    66	Repeat until Lead QA confirms the file is correct.
    67	
    68	---
    69	
    70	## Phase 4 — Generate the Playwright spec
    71	
    72	Only proceed when Lead QA has confirmed the `.feature` file.
    73	
    74	Write the Playwright test to:
    75	- `e2e/tests/zimm/{area}/{JIRA-KEY}_{description}.spec.ts` — for standard tests
    76	- `e2e/tests/zimm/{area}/{JIRA-KEY}_{description}.p0.spec.ts` — for P0 tests
    77	
    78	Rules:
    79	- Files are TypeScript (`.spec.ts`) — the TS-only convention applies to E2E too.
    80	- Import Page Objects from `e2e/support/pages/` — never use raw selectors in the test file.
    81	- Selector priority in POMs: accessible selectors (role + accessible name, label, text) > semantic HTML attributes (alt, title) > `data-testid` (only when no semantics apply). See [.claude/rules/testing.md](../../rules/testing.md).
    82	- Import fixtures from `e2e/fixtures/` — never hardcode test data. Fixtures must be keyed by `SITE_ID` (Zimmermann has 8 storefronts across 11 active locales).
    83	- Test description must match the Scenario name in the `.feature` file exactly.
    84	- Use `waitForSelector` or `waitForResponse` — never `waitForTimeout`.
    85	- Under 200 lines — extract shared logic to `e2e/support/helpers/` if needed.
    86	- **Every `test()` call must carry two Playwright tags: the `.feature` file's `@area` tag AND
    87	  its `@{JIRA-KEY}` tag** from Phase 2, e.g. `test('...', {tag: ['@checkout', '@SFCC-142']},
    88	  async ({page}) => {...})`. The `@area` tag is what `develop`-targeted PRs use to run only the
    89	  specs relevant to a diff — see [.claude/rules/testing.md > Change-scoped
    90	  E2E](../../rules/testing.md#change-scoped-e2e-develop-targeted-prs-only). The `@{JIRA-KEY}`
    91	  tag is what lets `e2e-browserstack` scope a Zephyr-linked BrowserStack run to just this
    92	  story when its key is referenced on a PR — see [.claude/rules/testing.md > BrowserStack story
