Every message carries the full history; on a long thread the relevant signal gets buried in noise and quality quietly drops.\n102\t\n103\tThe rules:\n104\t\n105\t- **New conversation when the topic shifts.** Topics bleed across context and pollute each other.\n106\t- **Name conversations like files, not chat logs.** `checkout-fetch-pattern`, not \"SFCC stuff.\" Treat them as a structured archive you can navigate.\n107\t- **Aim for 8–10 named, focused threads**, not one 80-message thread called \"Zimmermann.\"\n108\t- **Claude.ai Projects share context across conversations** — use a Project for planning. **Claude Code uses the repo's rules/context files instead** (`CLAUDE.md` + the `.claude/` layer).\n109\t\n110\t- *IC discipline:* One topic per thread. The moment you notice yourself pasting unrelated context to \"remind\" Claude, you needed a new thread three messages ago.\n111\t- *Lead discipline:* At team scale, thread hygiene stops being about *your* signal and becomes about *shared* context. What lives in a personal thread is invisible to the squad; what needs to be shared belongs in the Project or the rules layer, not buried in someone's chat history. Decide, as lead, what's personal-thread vs shared-artifact — and make that call explicit so the team isn't guessing.\n112\t\n113\t---\n114\t\n115\t## 6. The planning layer — your codebase's constitution\n116\t\n117\tThis is where the quality ceiling is actually set. In the training it was a `.claude/` structure; on your project it's the equivalent rules-and-context layer (section 16 maps the names).\n118\t\n119\t### `CLAUDE.md` is a contract, not a readme\n120\t\n121\tIt tells Claude exactly **what to build**, **how to build it**, and **what NOT to do**. Claude Code reads it at the start of *every* session. It is the entry point every prompt begins from.\n122\t\n123\t- **Use Claude to *critique* the contract, not rewrite it.** Ask what's wrong; fix one problem at a time. If you let Claude rewrite it wholesale you get a file that reflects Claude's assumptions, not your decisions.\n124\t- **Each fix should change *structure or specificity*, not wording.** Polishing sentences is procrastination. If your edit didn't change what Claude can or can't do, it wasn't a real edit.\n125\t\n126\t### One topic per file — a hard rule\n127\t\n128\tIf a file covers two things, Claude gets confused about which one applies. So: `build-spec.md`, `solution-architecture.md`, `auth-spec.md`, `design-system.md`, `api-patterns.md`, `component-registry.md` — one concern each. The training's own structure split a `brief/` folder (the *what* and *how*) from a `rules/` layer (the enforceable constraints Claude checks against).\n129\t\n130\t**Monolith vs split is a real decision.** Both are defensible *if you can defend it* — but the split is where a serious project lands. A monolithic file and a split set of files produce genuinely *different* Claude Code output. Know why you chose yours.\n131\t\n132\t### `build-log.md` is memory, not documentation\n133\t\n134\tClaude reads it at the start of every session to know what state the project is in and what's already been done. It is how a fresh Claude Code session — with no memory of yesterday — picks up where you left off.\n135\t\n136\t### Define \"done\" — or Claude Code never stops\n137\t\n138\tClaude Code with no stopping condition keeps building components forever. If your file doesn't say what \"done\" looks like, Claude will invent more work. **Where does your file say what done is?** If it doesn't, that's a bug in the plan, not the tool.\n139\t\n140\t- *IC discipline:* Before you build, three questions must be *yes*: does Claude know exactly what to build, exactly how, and exactly what not to do? If any is no, fix it before you open Claude Code.\n141\t- *Lead discipline:* The planning layer is the highest-leverage thing you own. **This is a system, not a personal note.** A rule that isn't checkable is an aspiration Claude will ignore — police the difference across the whole `rules/` layer. And because two squads read the same files, ambiguity here isn't one dev's rework, it's a fork in the codebase. Owning this well is worth more than any component you'll personally write.\n142\t\n143\t---\n144\t\n145\t## 7. Gap-hunting before the build\n146\t\n147\t**Find every gap before Claude Code does. Every gap in your planning files costs time in the build** — and on a fixed-price job, that time comes out of margin.\n148\t\n149\t**Use two reviewers with different mindsets, in order:**\n150\t\n151\t1. **Claude.ai first** — the conversational reviewer. Prompt it as a senior engineer handing the project to a junior who'll build it with Claude Code: *\"Find every place Claude Code would have to make an assumption because I haven't told it what to do. Be specific. Don't be kind.\"*\n152\t2. **Claude Code second** — the builder's reviewer. *\"Read all files. Do not write code yet. Tell me: every assumption you'd have to make; every instruction that conflicts with another; every topic the files don't cover; check framework versions are current LTS; check the sample code is correct and uses our methodology; any flaws with downstream impact. Reference the file and line for each.\"*\n153\t\n154\t**The contrast between what Claude.ai flags and what Claude Code flags is the lesson.** Claude.ai catches conceptual holes; Claude Code catches build-breaking ones. Whatever gaps remain after both — they're *knowable*, and knowable gaps are the ones you can close.\n155\t\n156\t**The distinction that separates real work from theatre:** *\"Is that gap fixed now, or did you just acknowledge it?\"* Acknowledging a gap in conversation and moving on is the seductive failure. Fixing means the file changed.\n157\t\n158\t- *IC discipline:* Run both reviewers on your own stories before you build. \"What did Claude just find that I thought was obvious?\" is the most useful question you'll ask all day.\n159\t- *Lead discipline:* Institutionalize the two-reviewer pass as a squad ritual before any sprint. And guard against acknowledge-don't-fix at the team level — in review, don't ask \"did Claude flag anything?\", ask \"show me the file line you changed.\"\n160\t\n161\t---\n162\t\n163\t## 8. Scaffolding discipline\n164\t\n165\t**Do not scaffold by hand.** Running the framework's project generator manually (`create-next-app` in training; the PWA Kit generator on your project) *skips the brief entirely* — Claude Code won't wire up your design tokens, routes, env vars, or folder structure, and you'll spend Wednesday paying for it.\n166\t\n167\tInstead: let Claude Code **read the brief and execute every setup step**, as an explicit numbered sequence — configure design tokens, set up fonts, create the folder structure from the architecture file, wire env placeholders, create the build-log with a setup checklist as its first entry. **Confirm each step; list every file created at the end.**\n168\t\n169\t- *IC discipline:* After generation, don't trust — verify. Open the token config; missing tokens cause compile errors downstream. A green scaffold checklist exists precisely so this moment is fast and unambiguous.\n170\t- *Lead discipline:* The scaffold sets conventions the whole squad inherits. Get the folder structure, token config, and env contract right *once*, centrally — every shortcut here is multiplied across every developer who builds on top of it.\n171\t\n172\t---\n173\t\n174\t## 9. The build loop — the core craft\n175\t\n176\tThis is the part that \"makes the methodology different from just prompting.\" Everything above exists to make this loop clean.\n177\t\n178\t### 9.1 Atomic design, bottom-up\n179\t\n180\tBuild in layers: **layout primitives → atoms → molecules → components.** The lower layers are the foundation; you generate them from the design-system spec *first*, review them carefully, and everything above imports them.\n181\t\n182\t### 9.2 The story skill — consistency at scale\n183\t\n184\tA **skill is a reusable Claude prompt** that produces consistent, buildable output given a component name. You build one `story-skill` conversation and drive it with a command: `/create-story [ComponentName]`.\n185\t\n186\tA good story is **thin — intent and constraints, not implementation detail.** The non-negotiable format:\n187\t\n188\t- Follows the story template exactly.\n189\t- References the *correct* design file and the *correct* data stub (or none, for static components).\n190\t- **AC describes behaviour, not implementation** — something a tester can verify without asking a developer what it means.\n191\t- **Always includes happy path + loading-state AC + error-state AC.** Three states, every time.\n192\t- **Flags anything uncertain rather than inventing it.**\n193\t\n194\t**The skill is only as good as its prompt — and the prompt gets better every time you find a gap in its output.** Run it, find what it invented or left vague, refine one thing, run again. The second output is tighter. *That iteration is the lesson* — it's the same feedback loop as section 9.6, applied to your tooling.\n195\t\n196\t### 9.3 Generate is 10%. Review is 90%.\n197\t\n198\tGenerating a component or a story takes a minute. **The work is the review.** A bad story generates a bad component; five minutes reviewing a story now saves an hour tonight.\n199\t\n200\t**Hard rule: no one builds from a story they haven't personally read and checked.** Not you, not anyone on the squad.\n201\t\n202\t### 9.4 The registry — import, don't reinvent\n203\t\n204\t`component-registry.md` lists what exists, where it lives, and its data source. Before building anything: **check the registry and import what's there — do not rebuild atoms inline.** After building: **update the registry.**\n205\t\n206\tThe test: *\"If Claude Code opens this repo tomorrow with no memory of today, does it find a registry that tells it what's already built?\"* On a solo project that's a convenience. **On two squads it's the difference between reuse and three developers building three different `StatusBadge`s.**\n207\t\n208\t### 9.5 The loop itself\n209\t\n210\t> **story → build → review → correct → commit.** One story, one prompt, one review, one commit.\n211\t\n212\tThe build prompt pattern, every component: *read the registry, read the design-system rules, read this component's story, read the design file — confirm what you read before writing a single line of code — build exactly as specified, import from the registry, don't reinvent.*\n213\t\n214\t- *IC discipline:* Run the loop honestly on your own components. When Claude Code does something the story didn't specify, that's a defect in the story — go fix the story (9.6), don't just patch the code.\n215\t- *Lead discipline:* The loop is what you're teaching and enforcing. In review, verify the loop *ran*: \"Did Claude Code read the story before building, or did you just hand it the design file?\" A squad that skips the story and prompts from the design file is doing exactly the thing the methodology exists to prevent.\n216\t\n217\t### 9.6 The feedback loop that hardens the rules layer\n218\t\n219\tThe most important habit for long-term quality:\n220\t\n221\t> **\"Find one place where Claude Code made a decision you didn't specify. What would you add to the AC or the rules to prevent that next time?\"**\n222\t\n223\tEvery correction is data. A correction you make once and forget is a correction you'll make fifty times across the codebase. A correction you *push back into the story template or the rules layer* is made once, forever, for the whole squad. This is how the rules layer becomes real instead of aspirational — and it's pure Lead leverage.\n224\t\n225\t---\n226\t\n227\t## 10. The quality bar and the anti-patterns\n228\t\n229\t### The hardening checklist — every component, non-negotiable\n230\t\n231\tRun this on every component before it's \"done.\" (Stack names are translated to your project; the *intent* is verbatim from training.)\n232\t\n233\t- **Mobile layout at 375px** — actually open dev tools and check.\n234\t- **Loading state present — a skeleton, not a spinner.**\n235\t- **Error state present — a proper error component *with retry*.**\n236\t- **No hardcoded hex values — design tokens only.**\n237\t- **No TypeScript `any`** — strict mode on. *(This is already your default per your working style — hold the squad to it.)*\n238\t- **Deployed and resolving — matches local, not just running locally.**\n239\t- **Registry updated with everything built.**\n240\t\n241\t### Anti-patterns to catch on sight\n242\t\n243\t- **Over-engineering.** A static banner that should be ~25–35 lines of JSX comes back as 120 — that's Claude over-engineering; simplify it. If a trivial component takes too long to build, the problem is usually the atom layer underneath, not the component.\n244\t- **Logic in the wrong place.** Derive calculated values (a `percentUsed`, a `daysRemaining`) **in the component, not the hook** — or wherever your `api-patterns` rule specifies. The point isn't the specific rule; it's *consistency* — watch for Claude Code *drifting* from the pattern across components.\n245\t- **Fetch inside the component.** Data-fetching follows the shared pattern (a hook / service layer), *not* inline in the component.\n246\t- **UI state vs server state confusion.** A local toggle is local UI state — it does not round-trip to the API. Know which is which and don't let Claude blur them.\n247\t- **Invented data sources.** A *derived* component (one whose data comes from other components' data) does not get its own stub or its own API call. If Claude invents one, **fix the story, not the code.**\n248\t- **Rebuilt assets.** Complex SVGs / illustrations get copied from the design file verbatim — don't let Claude \"recreate\" them from scratch.\n249\t- **Hardcoded-per-item logic.** Icon or variant selection driven by a `type` enum, not a hardcoded branch per item.\n250\t\n251\t- *IC discipline:* Harden your own work to this bar before you'd dream of asking anyone else to.\n252\t- *Lead discipline:* This checklist is your review rubric and your definition of team-done. The over-engineering and drift checks especially are things *only a senior eye catches* — juniors accept whatever compiles. That catch is a large part of what you're paid for.\n253\t\n254\t---\n255\t\n256\t## 11. Shipping discipline — pragmatism under a fixed-price clock\n257\t\n258\tThe training's pragmatism is directly relevant to a fixed-price, deadline-bound delivery:\n259\t\n260\t- **Deploy first.** A local build that hasn't shipped is invisible — to the review, to the client, to everyone. *\"A local build that hasn't shipped is invisible to the regroup.\"*\n261\t- **A partial-but-hardened deliverable beats a complete-but-broken one.** *\"A deployed page with a loading state beats a perfect local component.\"* *\"A partial portal with hardened components beats a complete portal with broken states.\"*\n262\t- **Descope — never cut.** When something runs over: reduce scope (the complex chart becomes a data table — same data, no charting library), commit a loading-skeleton placeholder, and move on. **Never delete the component entirely.** Something honest in place beats a hole.\n263\t- **The 20-minute rule.** If a fix will take more than ~20 minutes right before a deadline, it's not worth doing before the milestone. Ship what's done and done well; log the rest.\n264\t- **Compare against the design, side by side.** Design file on one half of the screen, live URL on the other. Divergence you can't see, you can't fix.\n265\t\n266\t- *IC discipline:* Make the descope call on your own work early and without ego. Running over at the 80% mark? Stop, commit a clean placeholder, move on.\n267\t- *Lead discipline:* You own the *triage* across the squad — what gets hardened, what gets descoped, what gets cut for the milestone. Protecting the quality bar under deadline pressure is the specific test of whether you're actually leading or just hoping. Hold the bar when it's inconvenient; that's when it counts.\n268\t\n269\t---\n270\t\n271\t## 12. Cross-cutting dimensions — the \"etc.\"\n272\t\n273\tThe user asked for the *etc.* explicitly. Rituals to run — review culture as delivery practice\n364\t\n365\tThe training's *regroup* is your review culture. On the project you're the facilitator, under real stakes. Scaffolding discipline\n\n**Do not scaffold by hand.** Running the framework's project generator manually (`create-next-app` in training; the PWA Kit generator on your project) *skips the brief entirely* — Claude Code won't wire up your design tokens, routes, env vars, or folder structure, and you'll spend Wednesday paying for it.\n\nInstead: let Claude Code **read the brief and execute every setup step**, as an explicit numbered sequence — configure design tokens, set up fonts, create the folder structure from the architecture file, wire env placeholders, create the build-log with a setup checklist as its first entry. **Confirm each step; list every file created at the end.**\n\n- *IC discipline:* After generation, don't trust — verify. Open the token config; missing tokens cause compile errors downstream. A green scaffold checklist exists precisely so this moment is fast and unambiguous.\n- *Lead discipline:* The scaffold sets conventions the whole squad inherits. Get the folder structure, token config, and env contract right *once*, centrally — every shortcut here is multiplied across every developer who builds on top of it.\n\n---\n\n## 9. The build loop — the core craft\n\nThis is the part that \"makes the methodology different from just prompting.\" Everything above exists to make this loop clean.\n\n### 9.1 Atomic design, bottom-up\n\nBuild in layers: **layout primitives → atoms → molecules → components.** The lower layers are the foundation; you generate them from the design-system spec *first*, review them carefully, and everything above imports them.\n\n### 9.2 The story skill — consistency at scale\n\nA **skill is a reusable Claude prompt** that produces consistent, buildable output given a component name. You build one `story-skill` conversation and drive it with a command: `/create-story [ComponentName]`.\n\nA good story is **thin — intent and constraints, not implementation detail.** The non-negotiable format:\n\n- Follows the story template exactly.\n- References the *correct* design file and the *correct* data stub (or none, for static components).\n- **AC describes behaviour, not implementation** — something a tester can verify without asking a developer what it means.\n- **Always includes happy path + loading-state AC + error-state AC.** Three states, every time.\n- **Flags anything uncertain rather than inventing it.**\n\n**The skill is only as good as its prompt — and the prompt gets better every time you find a gap in its output.** Run it, find what it invented or left vague, refine one thing, run again. The second output is tighter. *That iteration is the lesson* — it's the same feedback loop as section 9.6, applied to your tooling.\n\n### 9.3 Generate is 10%. Review is 90%.\n\nGenerating a component or a story takes a minute. **The work is the review.** A bad story generates a bad component; five minutes reviewing a story now saves an hour tonight.\n\n**Hard rule: no one builds from a story they haven't personally read and checked.** Not you, not anyone on the squad.\n\n### 9.4 The registry — import, don't reinvent\n\n`component-registry.md` lists what exists, where it lives, and its data source. Before building anything: **check the registry and import what's there — do not rebuild atoms inline.** After building: **update the registry.**\n\nThe test: *\"If Claude Code opens this repo tomorrow with no memory of today, does it find a registry that tells it what's already built?\"* On a solo project that's a convenience. **On two squads it's the difference between reuse and three developers building three different `StatusBadge`s.**\n\n### 9.5 The loop itself\n\n> **story → build → review → correct → commit.** One story, one prompt, one review, one commit.\n\nThe build prompt pattern, every component: *read the registry, read the design-system rules, read this component's story, read the design file — confirm what you read before writing a single line of code — build exactly as specified, import from the registry, don't reinvent.*\n\n- *IC discipline:* Run the loop honestly on your own components. When Claude Code does something the story didn't specify, that's a defect in the story — go fix the story (9.6), don't just patch the code.\n- *Lead discipline:* The loop is what you're teaching and enforcing. In review, verify the loop *ran*: \"Did Claude Code read the story before building, or did you just hand it the design file?\" A squad that skips the story and prompts from the design file is doing exactly the thing the methodology exists to prevent.\n\n### 9.6 The feedback loop that hardens the rules layer\n\nThe most important habit for long-term quality:\n\n> **\"Find one place where Claude Code made a decision you didn't specify. What would you add to the AC or the rules to prevent that next time?\"**\n\nEvery correction is data. A correction you make once and forget is a correction you'll make fifty times across the codebase. A correction you *push back into the story template or the rules layer* is made once, forever, for the whole squad. This is how the rules layer becomes real instead of aspirational — and it's pure Lead leverage.\n\n---\n\n## 10. The quality bar and the anti-patterns\n\n### The hardening checklist — every component, non-negotiable\n\nRun this on every component before it's \"done.\" (Stack names are translated to your project; the *intent* is verbatim from training.)\n\n- **Mobile layout at 375px** — actually open dev tools and check.\n- **Loading state present — a skeleton, not a spinner.**\n- **Error state present — a proper error component *with retry*.**\n- **No hardcoded hex values — design tokens only.**\n- **No TypeScript `any`** — strict mode on. *(This is already your default per your working style — hold the squad to it.)*\n- **Deployed and resolving — matches local, not just running locally.**\n- **Registry updated with everything built.**\n\n### Anti-patterns to catch on sight\n\n- **Over-engineering.** A static banner that should be ~25–35 lines of JSX comes back as 120 — that's Claude over-engineering; simplify it. If a trivial component takes too long to build, the problem is usually the atom layer underneath, not the component.\n- **Logic in the wrong place.** Derive calculated values (a `percentUsed`, a `daysRemaining`) **in the component, not the hook** — or wherever your `api-patterns` rule specifies. The point isn't the specific rule; it's *consistency* — watch for Claude Code *drifting* from the pattern across components.\n- **Fetch inside the component.** Data-fetching follows the shared pattern (a hook / service layer), *not* inline in the component.\n- **UI state vs server state confusion.** A local toggle is local UI state — it does not round-trip to the API. Know which is which and don't let Claude blur them.\n- **Invented data sources.** A *derived* component (one whose data comes from other components' data) does not get its own stub or its own API call. If Claude invents one, **fix the story, not the code.**\n- **Rebuilt assets.** Complex SVGs / illustrations get copied from the design file verbatim — don't let Claude \"recreate\" them from scratch.\n- **Hardcoded-per-item logic.** Icon or variant selection driven by a `type` enum, not a hardcoded branch per item.\n\n- *IC discipline:* Harden your own work to this bar before you'd dream of asking anyone else to.\n- *Lead discipline:* This checklist is your review rubric and your definition of team-done. The over-engineering and drift checks especially are things *only a senior eye catches* — juniors accept whatever compiles. That catch is a large part of what you're paid for.\n\n---\n\n## 11. Shipping discipline — pragmatism under a fixed-price clock\n\nThe training's pragmatism is directly relevant to a fixed-price, deadline-bound delivery:\n\n- **Deploy first.** A local build that hasn't shipped is invisible — to the review, to the client, to everyone. *\"A local build that hasn't shipped is invisible to the regroup.\"*\n- **A partial-but-hardened deliverable beats a complete-but-broken one.** *\"A deployed page with a loading state beats a perfect local component.\"* *\"A partial portal with hardened components beats a complete portal with broken states.\"*\n- **Descope — never cut.** When something runs over: reduce scope (the complex chart becomes a data table — same data, no charting library), commit a loading-skeleton placeholder, and move on. **Never delete the component entirely.** Something honest in place beats a hole.\n- **The 20-minute rule.** If a fix will take more than ~20 minutes right before a deadline, it's not worth doing before the milestone. Ship what's done and done well; log the rest.\n- **Compare against the design, side by side.** Design file on one half of the screen, live URL on the other. Divergence you can't see, you can't fix.\n\n- *IC discipline:* Make the descope call on your own work early and without ego. Running over at the 80% mark? Stop, commit a clean placeholder, move on.\n- *Lead discipline:* You own the *triage* across the squad — what gets hardened, what gets descoped, what gets cut for the milestone. Protecting the quality bar under deadline pressure is the specific test of whether you're actually leading or just hoping. Hold the bar when it's inconvenient; that's when it counts.\n\n---\n\n## 12.
