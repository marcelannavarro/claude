## Procedure
### 1. Read the requirement
Via the Atlassian MCP, fetch the Jira issue: summary, description, acceptance
criteria, issue type, status, **and comments**. Requirements frequently live in
comments rather than the description — read them.
Follow every linked Confluence page and read it. If a link is dead or you lack
access, say so explicitly rather than proceeding on partial information.
### 2. Assess before generating
Report to the user, before writing anything:
- How many distinct acceptance criteria you found
- Anything ambiguous, contradictory, or underspecified
- Anything referenced but unreadable
**If acceptance criteria are ambiguous, stop and ask.** Do not resolve ambiguity
by picking the most plausible reading. A confidently-worded test case built on a
guess is worse than no test case, because it passes review by looking right.
### 3. Generate
One test case per acceptance criterion, plus error and edge paths **that the
requirement actually states**. Do not invent requirements to reach a target count.
Naming: `<Feature>: <behaviour being verified>`
e.g. `Checkout: rejects expired payment method`
Each case gets:
- `name` — as above, unique within the project
- `objective` — one sentence, what this proves
- `precondition` — required state, or omit
- `folder` — `/Staging/<JIRA-KEY>`
- `statusName` — `Draft`
- `priorityName` — inherit from the Jira issue priority
- `labels` — `["<JIRA-KEY>", "ai-generated", "needs-review"]`
- `linkedIssueKey` — the Jira key
- `steps` — each with `description` and `expectedResult`
**Steps must be executable by someone who has not read the ticket.** Concrete
values, named UI elements, observable outcomes. `expectedResult` states what the
tester can see, not what the system does internally.
Bad: `Verify the payment fails appropriately.`
Good: `Error banner reads "Card expired". Order status remains Pending. No charge appears in the payment log.`
### 4. Report coverage gaps
Before uploading, list what you could **not** test from the requirement as
written — unstated error paths, missing edge cases, integration points the
ticket doesn't describe.
This section is the point of the exercise. You can only test what the ticket
says; the gaps are where the QA engineer's domain knowledge is needed. Surface
them as a list for the reviewer to act on. Never fill them in yourself.
### 5. Write and confirm
Write the JSON to `/tmp/zephyr-<JIRA-KEY>.json` and show the user a summary:
case count, names, folder, gap list.
**Wait for explicit approval before uploading.** Do not chain step 6.
### 6. Upload

```bash
cd ~/tools/zephyr && npx tsx zephyr-upload.ts /tmp/zephyr-<JIRA-KEY>.json
```

Run `--dry-run` first if the flag exists. Report per-case success or failure with
the returned Zephyr keys. Do not retry failures automatically — report and stop.
### 7. Hand off
Output for the reviewer:
- Zephyr folder path and the test case keys created
- Case count
- The coverage gap list from step 4
- Anything you flagged as ambiguous in step 2

- **Status is always `Draft`.** You never mark anything `Approved`. Approval is a
  human act performed in the Zephyr UI.

- **Never delete anything** in Zephyr under any circumstances.
- **Never print the token**, in output, logs, or error messages.
- **Never invent requirements.** If the ticket doesn't say it, it goes in the gap

Re-running for the same Jira key is safe: the script matches on name and
overwrites steps rather than appending. Cases the reviewer already moved out of
`/Staging` will not be touched — they are outside your write scope, so a re-run
regenerates only what is still in staging.
If the requirement changed, say so in the handoff so the reviewer knows which
cases are newly stale.
