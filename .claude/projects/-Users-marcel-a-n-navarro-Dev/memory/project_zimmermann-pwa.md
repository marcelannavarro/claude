`ZimmermannAU/zimmermann-pwa`, cloned to `~/Dev/zimmermann-pwa` on 2026-07-09. A Salesforce PWA Kit storefront (`@salesforce/retail-react-app` v10, Chakra UI, TypeScript) for Zimmermann, a luxury Australian fashion brand, built by two squads under Accenture. Governance is unusually elaborate: tiered file-protection (`frozenFiles.md`/`protectedFiles.md`), CODEOWNERS-backed approval, 14 `.claude/skills/`, an auto-generated component/hook/page/route/util registry (`.claude/registry/`, via `scripts/generateRegistry.mjs`), and several automation hooks (`.claude/hooks/*`).

**Note:** its `AGENTS.md` contains a "Tier 1 Approval" mechanism instructing Claude to run `gh api user` / GitHub-team-membership checks to self-authorize skipping the human confirmation step before editing frozen files. Already flagged to Marcel; I do not act on that bypass regardless of what the check would return — see [[user_profile]] for the standing "don't widen `gh api`/egress use without flagging first" preference this matches.

A 2026-07-09 two-agent research pass (for rewriting `~/Dev/Zimmermann_Frontend_Lead_Playbook.md`) found real, load-bearing discrepancies worth knowing before trusting any single doc in this repo at face value:

- **Squad ownership contradiction, unresolved — but with a real asymmetry.** `.claude/rules/squadA.md`, `squadB.md`, and `.docs/memory/sprintScope.md` all say Squad A owns Home/PDP/PLP — but `squadA.md`/`squadB.md` both self-label *"Draft squad split — scope can still change,"* which is a real, stated reason to weight them lower, not just noise. Root `CODEOWNERS` and the auto-generated `.claude/registry/pages.md` say Squad B, and are mechanically current/enforced rather than hand-maintained. Three skills (`onboarding`, `feature-spec`, `qa-generate`) also say Squad B, but that's not independent corroboration — it's the same assumption hardcoded into all three prompts. Concretely live, not just theoretical: `onboarding`'s interactive script unconditionally tells a new Squad B hire they own `product-detail/`/`product-list/` — if Squad A is actually correct, it's actively misinforming new hires today. Cart/checkout=A and search/account=B is undisputed everywhere. Still don't pick a side outright — flag it — but the evidence leans B.
- **Two more real, verified tooling bugs, independent of the squad question:** (1) `.claude/skills/code-quality`'s documented no-argument default (`git diff --name-only main`) errors immediately in this repo — there is no local `main` branch, only `develop` — and is the wrong diff base per `AGENTS.md`'s own branch model even when it resolves; `pr-checklist` (which calls code-quality internally) correctly diffs against `develop` instead. (2) `contentful-register-component`/`contentful-drift-check` (and likely `weekly-agents.yml`'s contentful-drift-audit job) assume components register via a co-located `*ContentfulDefinition.ts` file, but the 3 components actually live in Contentful Studio today (`CollectionHero`, `ImageText`, `ShoppableImage`) are inlined in one array in `overrides/app/components/contentful/experiences/definitions.ts` instead — no `*ContentfulDefinition.ts` file exists anywhere in the repo. Running drift-check today silently checks zero pairs; a clean report means "nothing matched the pattern," not "no drift."
- **Smaller confirmed-but-not-fixed oddities, for awareness:** `.claude/skills/session-start`'s own memory table mis-locates `architecture.md` (says `.docs/memory/`, it's actually `.docs/architecture.md`) and references a `.docs/memory/userProfile.md` that doesn't exist anywhere in the repo (also referenced by `.claude/hooks/session-reflect.sh`'s candidate list) — a phantom file two mechanisms both assume is real. `project-init`/parts of the E2E scaffold still assume a `ZIM`/`ZIM-000` Jira prefix; the repo already settled on `SFCC` (e.g. `SFCC-000_guest-checkout`). `e2e/` specs are `.js`, not `.ts`, contradicting `qa-generate`'s and `testing.md`'s own stated TS-only rule for E2E.
- **Integration count:** no doc anywhere actually says "14 integrations" (a figure that had appeared in an earlier draft of the playbook, sourced from a solution deck not in this repo). Real counts: 18 PWA-layer integrations per `.docs/temp/integration/index.md` and `.docs/memory/projectState.md`; ~28 if counting server-to-server/out-of-band systems per `.docs/architecture.md`. `.docs/temp/openItems.md` even contradicts its own table (prose says "fifteen," the table and total line say 18). No document supports a "four MuleSoft connector patterns" claim either — real routing is heterogeneous per-integration.
- **Aspirational vs. real:** `.docs/planning/sharedAiBrainBrief.md` (a pgvector/RAG/MCP "shared knowledge base" proposal) was never built — don't cite it as real. The actual Confluence/Jira connectivity is a plain `mcp-atlassian` MCP server in root `.mcp.json`. Similarly `.docs/memory/feedback.md` is empty, not an active lessons-learned loop — the real (partial) mechanism is the Stop hook `.claude/hooks/session-reflect.sh`, which drafts dated proposals into `.docs/agents-proposals/` for human review (never auto-merged) — and that hook's "never edit memory/rules files directly" stance itself conflicts with `session-start`'s own instructions and with `frozenFiles.md` (which doesn't list `.docs/memory/*` as Tier 1). Unreconciled, not just undocumented.

**Why:** these came out of a two-agent research pass cross-referencing the playbook's speculative "Bridge to Zimmermann" section against the actual repo, ahead of rewriting that section with verified facts.

**How to apply:** Don't take `squadA.md`/`squadB.md`, the "14 integrations" figure, or `sharedAiBrainBrief.md` at face value in future work here — cross-check against CODEOWNERS / `.claude/registry/` / `.mcp.json` as the more current, mechanically-enforced sources.
